# Аудит устойчивости соединений и RAM — 2026-10-15

## Критическое ревью — 2026-10-18

Задержки YouTube устранены по сообщению владельца. Его транспортные тюнинги
повторно не менялись. Проверены требования BG-01/BG-03/BG-04/BG-06,
двухуровневая топология и совместное размещение. Рабочие серверы не изменялись.

Исправлено:

- **P1: обход access-аутентификации через публичный общий 443.** Matrix может
  разрешить публичный вход, а Squid-терминатор обезличивает адрес в loopback.
  Ранее посторонний клиент мог обратиться прямо к transit SNI и получить
  `200 Connection established` без credentials; это воспроизведено локально.
  Оба TLS-терминатора теперь проверяют входной `$proxy_protocol_addr` по IP
  access-узлов до отправки потока бэкенду. `$remote_addr` не восстанавливается,
  исходящий PROXY-заголовок остаётся обезличенным. Matrix сохраняет общий порт.
- **P1: разные автогенерированные секреты MTProxy за одним балансировщиком.**
  Независимая генерация на каждом upstream создавала разные credentials,
  тогда как access выбирал произвольный upstream. Повторное соединение с тем же
  клиентским секретом могло попасть на несовместимый бэкенд. Теперь используется
  один общий секрет: inventory, затем существующий конфиг, затем разовая
  генерация при полном отсутствии. Разные существующие значения и частичная
  ротация отвергаются до изменения служб. Отключённые MTProxy-бэкенды исключены
  из relay upstream. Default SNI — `max.ru`; домен внутри секрета проверяется.
- **P1: неполное покрытие iptables.** IPv6 ранее не фильтровался, а при отдельном
  `squid_port` отсутствовал завершающий DROP для MTProxy 443. Добавлены оба случая,
  ip6tables-цепочка и восстановление обеих семей при загрузке. Ошибка restore
  больше не маскируется успешной следующей командой.
- **P1: удаление чужих объектов в `inet filter`.** Вместо удаления таблицы nftables
  атомарно обновляются только зарезервированные owner-цепочки и set. Чужая
  непустая таблица без признака владельца не захватывается. Дополнительные
  цепочки/правила сохраняются; reserved `input`, `forward`, `output`,
  `matrix_services`, `dns_clients` остаются под управлением проекта.
- **P2: отказ ротации Squid-журналов.** Правило пакета и отдельный `squid-aiproxy`
  совпадали по glob. `logrotate --debug` воспроизвёл `duplicate log entry`.
  Старый файл удаляется, единственное правило управляется по пакетному пути
  `/etc/logrotate.d/squid`. Повторная миграция проверена Ansible и logrotate.

Остаются открытыми:

- **P1: Basic Auth клиента не защищён внешним TLS.** Access использует `http_port`,
  маршрутизатор — TCP passthrough, примеры клиентов — `http://proxy:443`.
  TLS к целевому сайту начинается после CONNECT и не защищает заголовок
  `Proxy-Authorization`. Утверждение C2-FR-002 о защите credentials через CONNECT
  неверно для этой конфигурации. Нужен HTTPS-proxy listener/маршрут и проверка
  поддержки клиентами; действующий клиентский протокол в этом ревью не менялся.
  Свойства Basic описаны в [RFC 7617](https://www.rfc-editor.org/rfc/rfc7617.html).
- **P1: обнаружение перебора Squid-паролей не реализовано текущей конфигурацией.**
  `acquis.yaml.j2` отправляет записи с меткой `squid`, но проект не ставит
  соответствующий parser/scenario. SNI stream-журнал содержит транспортный status,
  а не HTTP 407, поэтому не заменяет разбор auth failures. SSH-детекция и bouncer
  API проходят тесты, но это не доказательство защиты proxy auth. Нужны parser,
  scenario и испытания отличия перебора от нормальных 407-challenge, чтобы
  не блокировать легитимные клиенты.
- **P2: обновление конфигурации не является полноценным rolling deployment.**
  `throttle: 1` у установки пакета не сериализует весь lifecycle узла;
  `tasks/squid-apply.yml` может остановить несколько Squid в одной задаче.
  Для требования доступности нужен порядок обновления/готовности узлов и
  тест отказа отдельного upstream, а не только локального manager.

Проверки этой ревизии: 25 unit-тестов, 25 сценариев resource preflight,
6 сценариев cluster-secret preflight (включая отключённый MTProxy, повторный прогон и отказ от
неявной ротации), миграция logrotate и syntax-check. Нативный стенд — отдельная
сеть WSL и cgroup с 400 МиБ при модельной RAM 961 МиБ, fake-TLS SNI `max.ru`,
96 CONNECT и 70-секундная пауза Telegram-реле. Посторонний источник отклонён
для transit, fake-TLS SNI и дополнительного публичного имени; разрешённые потоки
работают. Суммарный peak 300191744 байт, OOM kills = 0. Реальные Telegram DC и
рабочий YouTube не использовались. Сохранение nftables-объектов проверено дважды
без conntrack-правила: ядро этого WSL его не поддерживает. Полная IPv6-фильтрация
в ядре стенда не заявляется; матрица портов покрыта тестами.

## Проверка профиля 400 МиБ и первоначальной политики — 2026-10-16

Исходные минимумы Squid 64, nginx 48 и mtg 32 МиБ сохранены. Минимум CrowdSec
повышен до 192 МиБ: попытка использовать 160 МиБ в длительном испытании дала
таймаут локального API при живом процессе и нулевых OOM kills. Одного признака
«процесс запущен» для работоспособности недостаточно. Bouncer получает не меньше
24 МиБ. Прочие минимумы: Unbound 24, haveged 8, health 8, Keepalived 12 МиБ.

Остаток после минимумов распределяется по весам между включёнными службами;
явные переопределения не уменьшаются. Значения ниже минимумов отвергаются даже
на большом сервере. Число workers, FD Squid и сессии mtg ограничиваются отдельно.
Изменение `max_filedescriptors` входит в marker startup-параметров и вызывает
restart Squid: для него
[reload недостаточно](https://www.squid-cache.org/Doc/config/max_filedescriptors/).

Мягкий лимит Go у CrowdSec оставляет минимум 64 МиБ вне управляемой Go памяти.
Пул SQLite ограничен одним соединением через слияние `config.yaml.local` с
сохранением прочих настроек. Эти настройки описаны в документации
[Go](https://pkg.go.dev/runtime/debug#SetMemoryLimit) и
[CrowdSec](https://docs.crowdsec.net/docs/configuration/crowdsec_configuration/).

## Память и применение

Значения inventory в МиБ: Squid 64, nginx 48, unbound 24, mtg 32, CrowdSec 172,
bouncer 24, haveged 8, health 8. Полный upstream — 380 МиБ (398458880 байт).
На access mtg не запускается: 348 МиБ без VRRP / 360 МиБ с Keepalived 12.
Общий nginx учитывается полностью, включая обслуживаемые им соседние приложения.
ОС и отдельные службы соседей учитываются дополнительным резервом физической RAM.

Живые MemoryMax применяются без рестарта; их сумма уже обеспечивает общий предел.
Службы переходят в общую slice при штатном рестарте. Принудительный restart общего
nginx ради переноса не выполняется. Подтверждено на отдельной systemd-службе:
PID сохраняется при применении лимита, после restart меняется ControlGroup.

`proxy_max_connections=96` применяется к локальным TLS transit-серверам ai-proxy,
не к Matrix. Его проверка учитывает четыре nginx-слота на сеанс и резерв 128.
Это admission limit транзитных реле, а не обещание обслужить произвольное число
клиентов/скорость при заданной памяти. RAM ограничивается cgroup независимо от нагрузки.

YouTube и реальный Telegram-клиент на рабочих узлах в этом испытании не участвовали.
Фактическая первопричина конкретного рабочего отказа требует журналов узла за этот
период: OOM/cgroup events, nginx/Squid errors и CrowdSec decisions. Исправлены
найденные дефекты проекта; причинность каждого рабочего инцидента не заявляется.
В рабочем inventory domain allowlist не задан: блокировка `googlevideo.com`
в нём не подтверждена. При введении allowlist видео-CDN должны быть разрешены отдельно.

Сохранён инвариант graceful reload: глобальный `worker_shutdown_timeout` не задан,
чтобы принудительно не закрывать чужие туннели. Много реальных изменений при
непрерывно живущих соединениях всё ещё может удерживать несколько поколений workers;
фиксированная RAM не позволяет обещать неограниченное число таких поколений.
Безусловный reload устранён, общий RAM-предел и восстановление после OOM действуют.
