# Ansible Deployment

Автоматизированное развертывание AI Proxy на базе Squid.

Готовые конфигурации на вымышленных узлах, включая nginx, HTTPS/ACME, MTProxy,
DNS, firewall и systemd: [Servers/examples](../examples/README.md).
Они генерируются из действующих шаблонов и задач без рабочего inventory и секретов.

## Структура

```text
deploy/
├── inventory.yml.sample        # Полный публичный образец параметров
├── inventory.yml               # Рабочий inventory, исключён из Git
├── passwd.example              # Публичный образец пользователей
├── passwd                      # Рабочие хеши паролей, исключены из Git
├── playbook.yml                # Preflight, ресурсы, порядок настройки служб
├── templates/                  # Squid, общий SNI router, firewall, health, slice
├── tasks/
│   ├── ports.yml               # Диапазоны портов, общий 443, конфликты слушателей
│   ├── squid-apply.yml          # Применение Squid с учётом параметров запуска
│   ├── mtproxy-cluster.yml      # Общий секрет без неявной ротации
│   ├── health.yml              # Healthcheck и таймер
│   ├── shared-firewall.yml     # Контракт портов соседнего Matrix
│   └── resource-limits.yml     # Slice, индивидуальные пределы и OOM recovery
├── filter_plugins/             # План памяти, состав MTProxy/ACME
├── roles/
│   ├── nginx/                  # Access: SNI, HTTPS/ACME и MTProxy relay
│   ├── mtproxy/                # Upstream: общий nginx/Squid TLS; mtg опционален
│   │   └── tasks/daemon.yml    # Настройка mtg только при mtproxy_enabled=true
│   ├── dns_resolver/           # Unbound
│   └── crowdsec/               # CrowdSec, bouncer и собственные источники логов
├── scripts/                    # Применение контракта общих портов
├── tests/                      # Проверки preflight и реальные nginx/Squid туннели
├── diagrams/                   # Исходник PlantUML и готовый SVG
├── MTProxy.md
└── README.md
```

Общие шаблоны `00-sni-router.conf.j2` и `10-aiproxy-capacity.conf.j2`
находятся в `deploy/templates/`; обе роли используют именно их.
Конечные конфиги с путями установки перечислены в
[манифесте примеров](../examples/manifest.json).

## Повторное развёртывание и стоимость операций

Повторный запуск проверяет конфиги и состояние служб. Сетевая синхронизация,
пакетные транзакции и перечитывание systemd выполняются по необходимости.

| Операция | Прежде | Текущее поведение |
|---|---|---|
| CrowdSec Hub | 8 запусков `cscli` на узел при каждом деплое: update, list, 4 install, upgrade, list | При свежем неизменном снимке — 0 запусков `cscli`; срок по умолчанию 6 часов |
| Установка коллекций | Четыре отдельные команды на каждом запуске | Одна команда только для недостающих коллекций |
| Применение CrowdSec | Сравнение необработанного JSON списка коллекций | Сравнение содержимого активных коллекций, парсеров, сценариев и данных; новый индекс сам по себе не требует рестарта |
| Пакеты CrowdSec/bouncer | Две apt-транзакции | Одна транзакция с прежней политикой обновлений |
| Индекс apt | Роли nginx/MTProxy/CrowdSec безусловно обновляли индекс | Общий срок `apt_cache_valid_time=3600`; изменение репозитория CrowdSec обходит кеш |
| Facts | Полный сбор Ansible и повторный hardware setup | Один явный сбор min/hardware/network; сведения о RAM остаются актуальными |
| Проверка лимитов | Три удалённых цикла по службам: 24 вызова для 8 служб | Один вызов с одним `systemctl show` и чтением всех нужных `memory.max` |
| `daemon-reload` | Несколько безусловных вызовов в разных компонентах | По изменению unit/drop-in; проверка `NeedDaemonReload` восстанавливает незавершённое применение |
| Squid за nginx без Telegram | Один шаблон размещали роль и основной playbook | Единственный владелец шаблона — роль nginx |
| MTProxy secret | Повторные чтения после кластерного preflight | Используется уже согласованный секрет; отдельный запуск роли сохраняет fallback |

**Hub CrowdSec.** Параметры в `inventory.yml.sample`:

```yaml
crowdsec_hub_update_interval: 21600  # секунды; 0 — проверять при каждом деплое
crowdsec_hub_force_update: false    # true — разово проверить независимо от возраста
apt_cache_valid_time: 3600          # секунды; 0 — без кеширования индекса apt
```

Проверка Hub не зависит от `service_upgrades_enabled`. Потеря или изменение
активных файлов, отсутствие индекса, обновление пакетов и явный force вызывают
синхронизацию до истечения срока. Снимок хранится в
`/var/lib/aiproxy/crowdsec-hub.json`; повторный неизменный запуск его не переписывает.
Для первого снимка требуется одно подтверждённое применение движка.

Обновление зависимого парсера или файла данных правил обнаруживается даже при прежней
версии коллекции. Рабочая SQLite-база и её WAL/SHM/journal исключены из снимка: их
текущие изменения не являются обновлением Hub. Путь базы берётся из действующей
конфигурации CrowdSec, включая локальные переопределения. Перед применением выполняется `crowdsec -t`; успешное применение
подтверждается отдельно. При ошибке или прерывании состояние остаётся неподтверждённым:
следующий деплой повторяет применение. Нового фонового сервиса или таймера нет;
интервал ограничивает проверки при запуске деплоймента. CAPI продолжает работать
в действующем CrowdSec независимо от этого кеша.

Принудительная проверка, из корня проекта:

```bash
ansible-playbook -i Servers/deploy/inventory.yml Servers/deploy/playbook.yml \
  --tags crowdsec -e crowdsec_hub_force_update=true
```

Чтобы измерить продолжительность реальных задач на ваших узлах:

```bash
ANSIBLE_CALLBACKS_ENABLED=ansible.posix.profile_tasks \
  ansible-playbook -i Servers/deploy/inventory.yml Servers/deploy/playbook.yml
```

Проверки `nginx -t`, сертификатов, готовности Squid, обоих адресов DNS на upstream,
ограничений firewall и действующих cgroup остаются частью деплоя. Уменьшение числа
операций не основано на пропуске роли по признаку «пакет уже установлен».

Локальная проверка снимка измерена чтением на пяти рабочих узлах с CrowdSec 1.8.1:
0,21–0,45 секунды, RSS отдельного временного процесса около 18 МиБ. Это стоимость
проверки файлов, а не замер полного деплоя. В тесте повторного запуска роли
первый запуск вызвал 4 команды `cscli` и одно применение, второй — 0 и 0;
принудительная проверка неизменных правил — 3 команды и 0 применений.

Семантика команд: [CrowdSec Hub](https://docs.crowdsec.net/u/user_guides/hub_mgmt/),
[кеш индекса apt](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/apt_module.html).

## Требования

### Управляющий хост
- Ansible >= 2.9
- Коллекции: `ansible.posix`, `community.general`

### Целевые серверы

| Дистрибутив | Версия Squid из репозитория | Примечание |
|---|---|---|
| **Ubuntu 24.04 LTS** | 6.14 | Рекомендуется |
| Debian 13 (Trixie) | 6.x | — |
| Debian 12 (Bookworm) | 5.7 | Работоспособен: все директивы проекта приняты, приём участка под шифрованием и многопроцессный режим проверены на стенде |
| Ubuntu 22.04 LTS | 5.x | Требуется [Diladele PPA](https://docs.diladele.com/howtos/build_squid_on_ubuntu_22/repository.html) для 6.x |

**Системные требования:**
- Python >= 3.8
- systemd
- SSH доступ с правами root

### Пререквизиты: версии пакетов

| Пакет | Минимум | Максимум | Назначение |
|-------|---------|----------|------------|
| Squid | 5.7 | 6.x | Прокси-сервер. Минимум **измерен, а не назначен**: на 5.7 (Debian 12) проверены все директивы проекта. Проверяется при развёртывании — переменная `squid_min_version` |
| Unbound | 1.16 | 1.x | Кеширующий DNS-резолвер |
| Keepalived | 2.0 | 2.x | VRRP для access (опционально) |

**Фаерволы (upstream прокси):**

Бэкенд выбирается по состоянию ufw и дистрибутиву — в этом порядке:

| Условие на хосте | Бэкенд | Версия | Конфигурация |
|---|---|---|---|
| ufw активен (`ufw status` = active) | UFW | >= 0.36 | правила через `community.general.ufw` |
| ufw неактивен + Debian | nftables | >= 1.0 | `/etc/nftables.conf`; атомарно обновляются зарезервированные цепочки и set внутри `inet filter` |
| ufw неактивен + не Debian (Ubuntu, RHEL) | iptables / ip6tables | >= 1.8 | `/etc/iptables/aiproxy-upstream.rules` и `aiproxy-upstream-v6.rules`; отдельная `SQUID-PROXY` в каждой семье, восстановление `aiproxy-firewall.service` |

**Co-deployment.** nftables сохраняет таблицу `inet filter` и чужие объекты внутри неё.
Проект управляет цепочками `input`, `forward`, `output`, `matrix_services` и set
`dns_clients`; внешние изменения этих зарезервированных объектов не поддерживаются.
Непустую чужую таблицу без признака прежнего владельца deployment не захватывает.
iptables и ip6tables заменяют только собственные цепочки, не сбрасывая INPUT и
правила соседей. Применение каждой семьи атомарно; ошибка restore останавливает
deployment. Boot-unit восстанавливает обе семьи до старта сети и прокси.

При публичном 443 для Matrix сетевой экран не отделяет его клиентов от ai-proxy.
Поэтому оба приватных TLS-терминатора также проверяют входной `$proxy_protocol_addr`
по IP access-узлов. Проверка не восстанавливает `$remote_addr`: в Squid по-прежнему
поступает обезличенный PROXY-заголовок. Разрешения Matrix и анонимизация сохранены.

Ubuntu после чистой установки попадает в третью строку: ufw установлен, но не
активирован. Все три бэкенда закрывают один и тот же набор портов upstream-ноды
(Squid, MTProxy и DoH на общем 443/tcp) — доступ только с IP access-нод.
Результат проверяется на самой ноде задачей ограничения DoH на общем `443/tcp`
Читаются действующие правила ядра; отдельно выполняются DoH-запросы с access.

## Бюджет памяти узла

Бюджет на узел рассчитывается автоматически:
**min(max(RAM / 3, сумма минимумов включённых служб), 1 ГБ)**,
где 1 ГБ = 1000000000 байт. Треть RAM — целевой объём; минимумы имеют приоритет.
Явные пределы отдельных служб учитываются в нижней границе вместо их минимумов.
Для служб общий бюджет округляется вниз до целых МиБ.
Из доступной физической RAM также вычитаются резерв ОС и пределы соседних служб;
если остаток меньше потолка проекта, используется остаток.

| RAM узла | Access без VRRP | Upstream с MTProxy |
|---|---|---|
| 900 / 961 МиБ | 400 МиБ | 400 МиБ |
| 1200 МиБ | 400 МиБ | 400 МиБ |
| 1536 МиБ | 512 МиБ | 512 МиБ |
| 1967 МиБ | 655 МиБ | 655 МиБ |
| 3072 МиБ и больше | до 1000000000 байт | до 1000000000 байт |

Примеры включают CrowdSec, используют автоматические пределы и предполагают,
что после резервов достаточно RAM. При потолке 1 ГБ службам доступно 953 целых МиБ.

В сумму включены общий nginx, Squid, unbound, mtg на upstream, CrowdSec и bouncer,
haveged, проверка здоровья и Keepalived при его включении. Сначала выделяются
жёсткие минимумы из `filter_plugins/resources.py`, затем остаток распределяется
между включёнными службами. Если минимумы превышают треть RAM, бюджет повышается
до их суммы. Если они превышают потолок 1 ГБ, явный общий предел inventory или
остаток физической RAM после резервов, проверка до установки пакетов останавливает
деплоймент с требуемым и доступным объёмом; минимумы не уменьшаются.

| Служба | Минимум, МиБ |
|---|---|
| Squid | 64 |
| Unbound | 24 |
| dnsproxy (access) | 32 |
| nginx | 48 |
| mtg | 32 |
| CrowdSec | 192 |
| Firewall bouncer | 24 |
| haveged / проверка здоровья | 8 / 8 |
| Keepalived, если включён | 12 |

Полный upstream с MTProxy и CrowdSec требует 400 МиБ бюджета. Access без VRRP
требует 400 МиБ, с VRRP — 412 МиБ. К ним добавляются резервы ОС и соседей для
проверки физической RAM. Это минимумы планирования для ограниченной нагрузки;
работоспособность конкретного рабочего трафика требует проверки на узле.

`proxy_memory_budget_mb` в inventory задаёт только дополнительный меньший потолок
в МиБ: он не увеличивает рассчитанный бюджет или потолок 1 ГБ. `proxy_memory_limits` задаёт
частичные переопределения отдельных служб в МиБ. Явные значения сохраняются,
остальные рассчитываются автоматически; значение ниже минимума отвергается.

Жёсткие пределы задаются файлом `zz-aiproxy-resources.conf` каждой службы;
их проверенная сумма не превышает общего бюджета. `aiproxy.slice` дополнительно
ограничивает весь набор, `MemorySwapMax=0` исключает зависание из-за вытеснения
этих служб в swap. Работающие службы переходят в slice при ближайшем штатном
рестарте: общий nginx ради этого не перезапускается. До перехода проверяются
действующие пределы cgroup каждой службы; суммарный предел сохраняется.
Нужны systemd и cgroup v2 (`/sys/fs/cgroup/cgroup.controllers`).

Число workers Squid/nginx и размер таблиц FD Squid рассчитываются из памяти служб
и числа CPU. `proxy_max_connections: 96` и `mtproxy_max_connections` задают верхние
пределы; фактические значения дополнительно ограничены памятью и выводятся в отчёте
деплоя. При минимальном Squid 64 МиБ предел FD — 12288, транзитных сессий — до 96;
при mtg 32 МиБ — до 128 сессий, дополнительно ограниченных inventory.
Транзитный предел относится к локальным TLS-реле
ai-proxy; потоки Matrix и других проектов в эту зону не входят. Четыре nginx-слота
на сессию и резерв 128 проверяются отдельно. Предел mtg общий, не на IP.
Неограниченную нагрузку этот бюджет не обещает:
при перегрузке новые транзитные соединения отклоняются, сохраняя уже принятые.

Squid удерживает до 4 МиБ свободных объектов, а не половину своего лимита;
`cache_mem` равен 0 при выключенном кеше и 4 МиБ при включённом. Это размеры
кешей, а не предел живых соединений. CrowdSec сохраняется включённым.
`OOMPolicy=kill` и `Restart=on-failure` восстанавливают службу при аварийном OOM.
Локальный HTTP manager Squid проверяется таймером раз в 30 секунд; три отказа
вызывают асинхронный restart с cooldown. Недоступность внешнего сайта не служит
основанием для restart.

Обычный nginx reload сохраняет действующие соединения, включая соседние проекты.
Принудительный срок завершения старых workers не вводится: он оборвал бы чужие
туннели. Устранён безусловный reload из-за удаления и повторного создания SNI-записи
Squid на каждом прогоне. Изменение числа workers Squid требует restart.

Проверка до установки пакетов учитывает собственный план, действующие лимиты
чужих служб и системный резерв: их сумма не должна превышать физическую RAM.
Доля совместного размещения `mem_share_when_shared` — дополнительный потолок
(по умолчанию 1.0: действуют абсолютный предел проекта и реальные резервы,
а не прежнее произвольное деление 35/50%). Меньшая доля из inventory сохраняется.
`mem_foreign_reserved_mb` задаёт нижнюю границу резерва, а не заменяет измерения.
Приложение без MemoryMax требует явного резерва. На маленьком совместном узле
полный набор может быть отклонён; увеличить RAM или изменить размещение безопаснее,
чем понизить защитные минимумы.

Проверка: `systemctl show aiproxy.slice -p MemoryMax -p MemoryCurrent` и
`systemctl show squid nginx unbound mtg crowdsec crowdsec-firewall-bouncer -p MemoryMax -p ControlGroup`.
При отложенном переносе в slice `MemoryCurrent` самой slice показывает только
уже перенесённые службы: для остальных смотрите их действующие cgroup.

Разбор причин и границы проведённых испытаний: [аудит соединений](connection-audit.md).

Workers Squid/nginx ограничиваются памятью, а не только числом CPU. Unbound
использует по умолчанию один поток на маленьком бюджете и малые кеши с запасом
на накладные расходы malloc. MTProxy и bouncer получают GOMEMLIMIT=65% предела;
CrowdSec — минимум из 65% и предела за вычетом 64 МиБ. Это оставляет место для
исполняемого кода, файловых отображений и cgo, не учитываемых
[мягким лимитом Go](https://pkg.go.dev/runtime/debug#SetMemoryLimit).
Для SQLite CrowdSec пул ограничен одним соединением через `config.yaml.local`;
остальные локальные настройки сохраняются, PostgreSQL этот параметр не меняет.
Механизм слияния и параметр `max_open_conns` описаны в
[документации CrowdSec](https://docs.crowdsec.net/docs/configuration/crowdsec_configuration/).
Автоматический MemoryHigh=80% для Squid/nginx/Unbound снят: этот порог может
вызвать длительное вытеснение без освобождения рабочего набора приложением.

### Общий firewall с Matrix

Matrix публикует `/etc/shared-host/matrix-ports.json`. Обновлённый ai-proxy
устанавливает helper `aiproxy-apply-shared-ports`: он изменяет только дочернюю
цепочку Matrix в INPUT действующего nftables/iptables, сохраняя ограничения
Squid/DNS и CrowdSec. nftables template включает сохранённый фрагмент при
каждом redeploy; boot-unit восстанавливает iptables после владельца.
При активном UFW Matrix управляет собственными аддитивными правилами.
Неактивный UFW не считается применением портового контракта.

Проверка helper: `python -m unittest discover -s Servers/deploy/tests -p 'test_*.py'`.
Проверка синтаксиса после копирования образца в рабочий `inventory.yml`: `ansible-playbook -i inventory.yml playbook.yml --syntax-check`.

`inventory.yml.sample` содержит примеры всех поддерживаемых параметров и пояснения к каждому. Закомментированные переопределения сохраняют автоматический расчёт. Расширение `.sample` предназначено для образца: штатный YAML inventory plugin Ansible ожидает `.yml`, `.yaml` или `.json`, поэтому перед запуском скопируйте файл в `inventory.yml`.

Имена плейбуков, задач и обработчиков записываются по-русски, в форме действия в инфинитиве, без точки в конце. Сообщения описывают результат проверки или причину отказа по-русски; имена служб, переменных и протоколов сохраняются. При переименовании обработчика одновременно обновляются все ссылки `notify` и проверки, выбирающие задачу по имени.

## Шифрование участка access → upstream

Содержимое обращений защищено сквозным шифрованием клиента с целевым сервисом
независимо от этой настройки. Она закрывает другое: **заголовок `CONNECT`**, то есть
имя целевого сервиса. Без шифрования участка оно идёт открытым текстом, и наблюдателю
между узлами виден адресат обращения — скрыт состав обмена, но не то, к кому обращаются.

Включается парой переменных инвентори:

```yaml
squid_transit_tls: true
squid_tls_sni: "transit.internal"   # опознавательное имя, в DNS разрешаться не обязано
```

Без `squid_transit_tls` действует **false**: старый inventory сохраняет прежний
транспорт. TLS включается только явно. Имя проверяется до выпуска сертификата.
На Debian/Ubuntu при включении выбирается `squid-openssl`; уже установленная
сборка OpenSSL сохраняется и после отключения TLS. Замена пакета может перезапустить
Squid даже при `service_upgrades_enabled: false`, который управляет версиями,
а не выбором пакета. Сначала примените upstream, затем access.
Обновление Git или образца inventory само по себе не меняет запущенные службы.

**Материал.** Самоподписанный сертификат выпускается развёртыванием на управляющей
машине в `deploy/tls/` (каталог исключён из контроля версий — в нём закрытый ключ)
и раздаётся обеим сторонам: принимающей — сертификат и ключ, обращающейся — только
сертификат, служащий доверенным якорем. Выпуск именно на управляющей машине, а не
на узле: порядок обхода узлов плейбуком не определён, и выпуск на upstream оставил бы
access без доверенного материала при прогоне, начавшемся с access. Перед раздачей
`openssl verify -verify_hostname` проверяет имя и срок действия сохранённого
сертификата. Изменение SNI не перевыпускает старый сертификат автоматически;
при несовпадении сначала подготовьте новую согласованную пару сертификат/ключ.

**Две ветки приёма** — по устройству upstream-узла:

| Устройство upstream | Кто принимает TLS | Порт, к которому обращается access |
|---|---|---|
| Без nginx: `behind_nginx: false`, MTProxy выключен | сам Squid (`https_port`) | `proxy_port` |
| За nginx: `behind_nginx: true` либо включён MTProxy | nginx-терминатор за маршрутизатором SNI | `proxy_port`, обязательно 443 |

Настройка терминатора Squid не зависит от включения Telegram. Во второй ветке маршрутизатор разбирает имя из SNI и направляет соединение
локальному терминатору (`squid_tls_term_port`, по умолчанию 4444), тот снимает TLS
и передаёт поток Squid с новым PROXY-заголовком от loopback. Входной адрес
access-узла проверяется терминатором, исходный IP клиента в Squid намеренно
не восстанавливается.

Проверка подлинности принимающей стороны обязательна: `tls-no-default-ca` отсекает
системные удостоверяющие центры, `tls-cafile` задаёт единственный доверенный
сертификат, `tls-domain` — проверяемое имя. Сертификату, подписанному кем угодно
ещё, доверия нет.

Выбор транспорта применяйте полным плейбуком: отдельные теги nginx/mtproxy
не выполняют все задачи установки сборки Squid и раздачи CA.

Если неисправна связь одного access с конкретным upstream, задайте на этом access
`squid_upstream_hosts` списком проверенных узлов из группы `upstreams`.
Проверка непустоты, существования узлов и отсутствия повторов выполняется до
изменения служб. Это управляет родителями Squid; пулы DNS и MTProxy задаются отдельно.
При исключении одного родителя остальные продолжают обеспечивать резервирование.
Такая настройка обходит неисправный маршрут, но не устраняет причину сетевых потерь.

Выключение признака снимает терминатор с узла, а не оставляет его слушать порт.

**Ограничение сборки.** В Squid 6.14 с GnuTLS конфигурация `tls-domain`
проходит `squid -k parse`, но SNI не отправляется: nginx выбирает обычный Squid
вместо TLS-терминатора. В [исходниках Squid](https://github.com/squid-cache/squid/blob/v6/src/security/BlindPeerConnector.cc)
установка SNI находится в ветке OpenSSL. Проверка версии и рендеринг шаблона
не обнаруживают эту несовместимость. Плейбук проверяет OpenSSL до размещения
TLS-конфигурации; для RHEL нужна установленная сборка с `--with-openssl`.

Регрессионные проверки: `python3 -m unittest discover -s tests -p 'test_*.py' -v`.
Проверка настоящего демона запускается отдельно в Linux со Squid OpenSSL:

```sh
AIPROXY_TEST_SQUID=/usr/sbin/squid python3 -m unittest discover -s tests -p test_tls_peer_native.py -v
```

Она использует временные конфигурацию, PID и журналы, случайные loopback-порты
и локальный TLS 1.3 peer. Проверяются SNI, передача байтов CONNECT и отказ при
чужом CA/неверном имени сертификата. Нужны права запуска Squid и пользователь
`nobody` с группой `nogroup`. Это проверка одного участка, не нагрузочный тест
и не проверка всей цепочки nginx или доступа к Facebook в рабочей сети.

## HTTPS-прокси для клиентов

`squid_transit_tls` защищает только access → upstream. Для шифрования
Windows/Firefox → access включите отдельный HTTPS-вход на том же публичном 443:

```yaml
# Фрагмент inventory.yml: одинаковые параметры на обоих access.
all:
  children:
    access_proxies:
      hosts:
        access-01:
          ansible_host: 203.0.113.1
        access-02:
          ansible_host: 203.0.113.2
      vars:
        proxy_role: access
        enable_auth: true
        behind_nginx: true
        https_proxy_enabled: true
        https_proxy_hostname: proxy.example.com
        https_proxy_acme_enabled: true
        https_proxy_acme_email: admin@example.com
```

Имя может иметь два A-адреса или A/AAAA нескольких подготовленных access.
На каждом нужен доступный извне и со стороны соседей порт 80. Certbot использует отдельный именной HTTP-сайт в
`/etc/nginx/conf.d/aiproxy-https-acme.conf`, webroot `/var/www/certbot` и стандартные
пути `/etc/letsencrypt/live/<имя>/`. Default HTTP-сайты соседних проектов сохраняются.
Таймер Certbot продлевает сертификат, собственный deploy-hook проверяет nginx
и выполняет reload.

Узлы с включёнными HTTPS/ACME и одинаковым `https_proxy_hostname` автоматически
обнаруживаются в `access_proxies`. Каждый хранит собственные сертификат и закрытый
ключ. nginx сначала ищет HTTP-01 токен локально; если его нет, запрашивает у соседей
по их IP с тем же Host. Ответ соседнего узла не пересылается дальше. Поэтому
проверка проходит через любой опубликованный адрес, включая одновременное
продление двух независимых сертификатов. Пересылаются только GET/HEAD к
`/.well-known/acme-challenge/`, кеширование отключено; ключи не копируются.
Это обеспечивает доступность ответа на всех frontend-узлах, необходимую для
[HTTP-01](https://letsencrypt.org/docs/integration-guide/#picking-a-challenge-type).

Первый запуск выполняйте для обоих access вместе:

```sh
ansible-playbook -i inventory.yml playbook.yml --limit access_proxies
```

Плейбук использует `strategy: linear`: HTTP-сайты обоих узлов применяются до
запроса любого сертификата. До первого выпуска дополнительно проверяется путь
HTTP-01 через каждый соседний адрес. Частичный запуск допустим, когда соседние
HTTP-сайты уже подготовлены. После первоначального выпуска продление выполняют
локальные таймеры Certbot без Ansible. Добавляйте второй IP в DNS после проверки
HTTPS на обоих адресах; сам деплоймент DNS не меняет.

По умолчанию для связи используется `ansible_host`. Если SSH использует DNS-имя
или отдельный управляющий адрес, задайте на узле `https_proxy_acme_address`:
литеральный IPv4/IPv6 без порта, доступный соседям по 80/tcp. Общее имя прокси
для этой связи не используется, чтобы DNS-балансировка не возвращала запрос
тому же серверу. При одном участнике схема остаётся обычным локальным webroot.
Смешивание автоматического ACME и внешних сертификатов для одного общего имени
не поддерживается; для внешнего управления выключите ACME на всех его узлах.

Для сертификата, сопровождаемого вне проекта, оставьте
`https_proxy_acme_enabled: false` и задайте `https_proxy_certificate` (полная цепочка)
и `https_proxy_certificate_key` (ключ на сервере). Без переопределения используются
стандартные пути Let’s Encrypt. Имя и публичная цепочка проверяются OpenSSL;
ключ и вся конфигурация — `nginx -t`. Самоподписанный сертификат клиентского входа
не поддерживается. Нужен nginx с stream SSL, realip и ALPN (nginx ≥ 1.21.4).

Примените полный плейбук. В FoxyProxy выберите **HTTPS**, имя из
`https_proxy_hostname`, порт **443** и прежние логин/пароль. Тип HTTP на порту 443
не шифрует первый участок. Поддержка такого типа есть в
[Firefox ProxyInfo](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/proxy/ProxyInfo).
Проверить полную загрузку можно curl со сборкой, поддерживающей HTTPS-прокси:

```sh
# curl запросит пароль; сертификаты прокси и сайта проверяются штатно.
curl --proxy https://proxy.example.com:443 --proxy-user USER --noproxy '' \
  --connect-timeout 10 --max-time 30 --output /dev/null \
  --write-out 'HTTP=%{http_code} bytes=%{size_download} exit=%{exitcode}\n' \
  https://www.facebook.com/
```

Маршрутизатор различает входы по SNI. TLS снимается на loopback
`https_proxy_local_port` (4445 по умолчанию); затем обычный Squid проверяет пароль.
Клиентский адрес сохраняется на access для ACL, а на upstream остаётся намеренно
обезличенным. Наружу не открывается новый порт; HTTP-прокси и SNI соседей продолжают
работать. Внешний CONNECT использует ALPN HTTP/1.1, протокол сайта внутри туннеля
выбирает браузер. Используются существующие лимиты nginx, зона сессий проекта и
расчёт четырёх слотов nginx на туннель. Нового постоянно работающего прокси-процесса
нет; Certbot запускается периодически для продления сертификатов.

Клиентский HTTPS и ACME по умолчанию выключены. При выключении HTTPS удаляются
только его собственные stream-фрагменты и HTTP-сайт ACME. Certbot-сертификат,
таймер и обработчик reload сохраняются: ими могут пользоваться другие сервисы.
Если имя больше не используется, удалите его сертификат на каждом access через
`certbot delete --cert-name proxy.example.com`, чтобы прекратить попытки продления.
Невалидные TLS-фрагменты откатываются до reload общего nginx.

Проверка настоящего nginx на случайных loopback-портах:

```sh
AIPROXY_TEST_NGINX=/usr/sbin/nginx \
AIPROXY_TEST_NGINX_STREAM=/usr/lib/nginx/modules/ngx_stream_module.so \
python3 -m unittest discover -s tests -p test_https_proxy.py -v

AIPROXY_TEST_NGINX=/usr/sbin/nginx \
python3 -m unittest discover -s tests -p test_acme_cluster.py -v
```

Проверяются общий SNI router, HTTPS CONNECT, ALPN, передача блоков данных,
сохранение адреса access-клиента, прежний HTTP-вход и отказ при неверном имени
сертификата. Это локальный функциональный тест, а не замер производительности.
Отдельный HTTP-01 тест запускает два nginx с разными webroot: проверяет оба токена
через оба адреса, отсутствие циклов, удаление токенов и сохранение чужого HTTP-сайта.

## Использование

0. Создайте рабочие файлы из образцов (оба исключены из контроля версий: они содержат
   действительные адреса и реквизиты доступа и раскрытию не подлежат):
   ```bash
   cp inventory.yml.sample inventory.yml
   cp passwd.example passwd        # затем наполнить: htpasswd -B -C 12 -bn user pass >> passwd
   ```

1. Отредактируйте `inventory.yml`:
   - Укажите реальные IP/hostname серверов в группах `access_proxies` и `upstreams`
   - Настройте переменные `allowed_domains` и `allowed_domain_patterns`
   - Задайте `keepalived_auth_pass`; `mtproxy_secret` можно оставить пустым — он
     сгенерируется один раз для кластера, только если секрета нет ни на одном upstream.
     Существующий общий секрет сохраняется; разные существующие значения требуют
     явного выбора общего `mtproxy_secret`, автоматической ротации нет.

2. Запустите playbook:
   ```bash
   ansible-playbook -i inventory.yml playbook.yml
   ```

3. Для отдельных групп:
   ```bash
   # Только access прокси
   ansible-playbook -i inventory.yml playbook.yml --limit access_proxies

   # Только upstream прокси
   ansible-playbook -i inventory.yml playbook.yml --limit upstreams

   # Только DNS
   ansible-playbook -i inventory.yml playbook.yml -t dns
   ```

## Управление пользователями (access)

Отредактируйте файл `passwd` перед развёртыванием:

```bash
# Добавить пользователя: bcrypt с фактором стоимости 12
htpasswd -B -C 12 -bn пользователь пароль >> passwd
```

Ключ `-C 12` обязателен: без него `htpasswd -B` берёт фактор стоимости 5 — по нынешним
меркам низкий. Вариант через `openssl passwd -apr1` не используется: он выдаёт MD5-crypt,
от которого проект ушёл в августе 2026 года.

Файл `passwd` лежит в рабочем каталоге и под контроль версий не попадает; на access-узлы
его копирует плейбук (тег `passwd`). Инвентори при заведении пользователя не правится.

## Переменные

| Переменная | Описание | По умолчанию |
|------------|----------|--------------|
| `proxy_port` | Внешний порт: за nginx обязательно 443; без nginx — настраиваемый порт прямого Squid | 443 (обе группы в образце инвентаря) |
| `squid_upstream_hosts` | Непустой список имён из группы upstreams без повторов; переопределяется для конкретного access, определяет его родителей Squid | Вся группа upstreams |
| `enable_auth` | Включить аутентификацию | true (access) |
| `enable_logging` | Включить журналирование | true (access) |
| `enable_caching` | Включить кеширование | true (access) |
| `allowed_domains` | Разрешенные домены (явный список) | см. inventory |
| `allowed_domain_patterns` | Разрешенные домены (regex) | см. inventory |
| `dns_servers` | Публичные DNS (plain DNS, порт 53) | 9.9.9.9, 8.8.8.8, 1.1.1.1 |
| `dns_extra_clients` | Клиенты DNS сверх группы `access_proxies` (список IPv4) | `[]` |
| `enable_keepalived` | Включить Keepalived (access) | false |
| `keepalived_vip` | Виртуальный IP | — (обязательно задать) |
| `keepalived_interface` | Сетевой интерфейс | auto (default gw) |
| `keepalived_state` | MASTER или BACKUP | per-host |
| `keepalived_priority` | Приоритет (100/90) | per-host |
| `read_timeout` | Предел ПРОСТОЯ туннеля: соединение закрывается после этого срока без передачи данных в обе стороны. Таймер переармируется при каждой передаче, активный обмен продлевает таймер простоя; отдельно действует абсолютный предел `client_lifetime` | 1 hour |
| `client_lifetime` | Абсолютный предел жизни клиентского соединения Squid. Обязан быть строго больше `read_timeout`, иначе рвать будет он и предел простоя перестанет действовать | 1 day |
| `client_idle_pconn_timeout` | Срок удержания неиспользуемого постоянного соединения от клиента | 60 seconds |
| `squid_positive_dns_ttl` | Срок хранения разрешённого имени в собственном кеше Squid. Лежит поверх кеша резолвера: очистка unbound на эти записи не влияет | 6 hours |
| `squid_negative_dns_ttl` | То же для отрицательных ответов. Короткий срок нужен, чтобы временный отказ разрешения имени не запирал обращения надолго | 30 seconds |
| `allow_direct_fallback` | Запасной прямой выход при недоступности ВСЕХ вышестоящих узлов. Умолчание запрещающее намеренно: прямой выход раскрывает целевому сервису адрес access-узла | false |
| `connect_fail_limit` | Неудачных попыток подряд, после которых вышестоящий узел помечается мёртвым | 2 |
| `connect_timeout` | Срок ожидания установления соединения с вышестоящим узлом | 5 (секунд) |
| `dead_peer_timeout` | Как часто мёртвый узел проверяется снова | 15 seconds |

## Порядок развёртывания

Playbook выполняет фазы в строгом порядке:

1. **Base setup** — apt, SSH, утилиты, sysctl, лимиты
2. **Бюджет памяти** — пределы служб от объёма RAM и проверка выполнимости плана.
   Не помещается — развёртывание **останавливается** здесь, до внесения изменений на узел
3. **DNS resolver** — unbound на каждой ноде
4. **Установить Squid** — пакет, systemd override, директории
5. **nginx/MTProxy** — **до** конфигурации Squid, чтобы освободить порты:
   - upstream: mtproxy role устанавливает nginx на :443, удаляет default site с :80
   - access: nginx role устанавливает nginx на :443, переконфигурирует Squid на :3128
6. **Squid config** — деплой конфигурации, reload/restart
7. **Firewall** — UFW/nftables/iptables (upstream)
8. **Keepalived** — VRRP failover (access)
9. **CrowdSec** — IPS с infrastructure whitelist

## DNS: Unbound и DoH

```text
Squid / ОС → access Unbound 127.0.0.1:53
                  ↓ DNS только по loopback
             dnsproxy 127.0.0.1:5353
                  ↓ HTTPS HTTP/2, проверка сертификата отключена
             upstream nginx :443 (SNI dns.transit.internal)
                  ↓ relay 127.0.0.1:4447, снятие PROXY-заголовка
             Unbound TLS 127.0.0.1:8443/q → dns_servers:53

Любой DoH-клиент → https://dns.example.com/q :443
                  ↓ SNI → nginx TLS 127.0.0.1:4446
                  ↓ HTTP/2 без TLS, только loopback
             access Unbound 127.0.0.1:5443 → та же цепочка upstream
```

На обоих уровнях обычный UDP/TCP DNS слушает только `127.0.0.1:53`.
Межсерверный DoH идёт через общий внешний `proxy_port` (443), доступный только
access и `dns_extra_clients`. Отдельный SNI направляет TLS через loopback relay
4447 в Unbound 8443; relay снимает PROXY-заголовок и проверяет ACL клиентов.
Порт 8443 за nginx наружу не открыт. DNS stamps фиксируют IP и SNI без DNS bootstrap. Публичный DoH
на access открыт всем, без авторизации и списка разрешённых клиентов; путь `/q`
поддерживает GET и POST в wire format RFC 8484 через HTTP/2.

Access обращается к upstream исключительно по DoH. В dnsproxy заданы DNS stamps со статическими
IP и SNI, `insecure: true`, пустые bootstrap/fallback; открытого резервного
DNS-тракта нет. Каждый запрос направляется upstream параллельно, используется
первый успешный ответ. Таймаут — 4 секунды, число обработчиков ограничено 64.
Проверка сертификата отключена намеренно по требованию владельца: шифрование
сохраняется, удостоверение личности upstream не выполняется. DNSSEC в Unbound
остаётся отдельной проверкой подписанных зон.

Между access и upstream используются постоянные HTTP/2-соединения поверх
**TLS 1.3**. Пул транспорта dnsproxy v0.86.0 повторно использует соединения и
закрывает их через 300 секунд без DNS-запросов; это отличается от таймаута
отдельного запроса (4 с). `tcp-idle-timeout` upstream Unbound также равен
300000 мс. После простоя следующий запрос создаёт новое TLS-соединение;
активный поток запросов не обрывается по возрасту соединения.

В Unbound 1.19 нет директивы `tls-protocols`: TLS 1.3 задаётся через отдельный
`/etc/unbound/openssl-doh.cnf` и переменную `OPENSSL_CONF` только для upstream
unbound.service. Общая политика OpenSSL узла и клиентский TLS публичного DoH
не меняются. Нативная проверка отклоняет TLS 1.2 и принимает TLS 1.3.
`tests/check_doh_idle.py` наблюдает реальное соединение более пяти минут,
проверяет сохранение до таймаута и новое соединение после него.
Реализация пула: [dnsproxy v0.86.0](https://github.com/AdguardTeam/dnsproxy/blob/v0.86.0/upstream/doh.go);
политика службы: [OpenSSL SSL configuration](https://docs.openssl.org/3.0/man5/config/#ssl-configuration).

Кеши Unbound следуют TTL зоны, `serve-expired` выключен. Транспорт dnsproxy
собственного кеша не ведёт. Минимумы памяти: Unbound 24 МиБ, dnsproxy 32 МиБ
только на access; транспорт входит в общий план и cgroup проекта. Потоки и кеши
Unbound рассчитываются из его лимита памяти. Подробные параметры с комментариями
приведены в [inventory.yml.sample](inventory.yml.sample).

Для публичного DoH задайте в `access_proxies.vars`:

```yaml
dns_doh_enabled: true
dns_doh_hostname: dns.example.com
dns_doh_acme_email: admin@example.com
```

Все A/AAAA имени должны вести на подготовленные access с доступными портами
80/443. Certbot выпускает отдельный сертификат и ключ на каждом access; HTTP-01
имеет локальный приоритет, при отсутствии токена обращается к соседу за один
переход. HTTP-сайты HTTPS-прокси и DoH имеют разные имена upstream и сосуществуют.
`certbot.timer` продлевает оба сертификата, deploy hook проверяет и перечитывает
nginx. TLS для публичных клиентов — 1.2/1.3, ALPN — `h2`.

Первый переход на DoH выполняйте **полным прогоном всех узлов**:

```bash
ansible-playbook -i inventory.yml playbook.yml -e service_upgrades_enabled=false
```

Сначала устанавливаются бинарники и готовятся отдельные staged конфиги,
SNI router upstream и firewall. Затем активируется и проверяется DoH upstream,
после него переключается access; только затем запускается Certbot. Системный `/etc/resolv.conf` переключается после успешного
DNS-запроса. Применённый digest фиксируется после проверки: прерванный прогон
не оставит конфигурацию на диске не применённой при повторном запуске.
Конфиги Unbound, dnsproxy и unit транспорта сначала записываются отдельно
от активных. Клиентский транспорт переключается после готовности upstream;
его фактическая работа проверяется запросом прямо на 5353, отдельно от кеша
Unbound. Для Unbound, транспорта и nginx хранятся подтверждения применённой
версии: при обрыве после записи файлов повторный прогон всё равно применит
изменения. Подтверждение nginx записывается только после корректного DoH-ответа.

Для применения изменений используйте полный прогон всех узлов. Отдельные
`--limit upstreams` или `-t dns` не выполняют весь межролевой порядок:
это пропустит подготовку зависимостей либо оставит access без старого DNS.

Готовность проверяется по локальным адресам и реальными DoH-запросами с access
к каждому upstream. Самопроверка по `ansible_host:53` удалена: у узла за NAT
этот адрес может отсутствовать на интерфейсах, а NAT hairpin — не поддерживаться.
После reload выполняется DoH-запрос через локальный публичный SNI-маршрутизатор
с **проверкой доверия и имени** сертификата access.

```bash
# Локальное разрешение и состояние служб access.
dig @127.0.0.1 example.com
systemctl status unbound aiproxy-doh
journalctl -u unbound -u aiproxy-doh -n 50

# Публичный DoH GET; проверка TLS включена.
curl --http2 --fail 'https://dns.example.com/q?dns=AAABAAABAAAAAAAAB2V4YW1wbGUDY29tAAABAAE' --output /tmp/dns-response.bin

# Действующие ограничения upstream.
iptables -S SQUID-PROXY | grep -E '443|8443|53'
# Для nftables: nft list chain inet filter input; nft list set inet filter dns_clients.
```

Нативные проверки: `tests/test_dns_doh.py` (Unbound, nginx, dnsproxy),
`tests/test_acme_cluster.py` (два имени и два IP), `tests/check_doh_budget.py`
(2000 запросов с параллелизмом 32 под реальным `MemoryMax=32M` в тестовой VM).

## Архитектура: nginx stream routing и Squid

![Deployment diagram](diagrams/README-deployment.svg)

### Access nodes

Публичный SNI router слушает общий 443 и передаёт исходный TLS-поток выбранному
локальному обработчику. Сам router TLS не завершает. При включённом
`https_proxy_enabled` отдельный терминатор принимает клиентский TLS 1.2/1.3
на loopback:4445 и передаёт HTTP CONNECT в Squid. Прямой HTTP-прокси остаётся
доступен через fallback того же публичного порта.

```text
Client → nginx:443 (ssl_preread + PROXY protocol)
            ├─ SNI=proxy.example.com → HTTPS term :4445 → Squid :3128
            ├─ SNI=max.ru / tgproxy.example.com → MTProxy relay :9443
            │     └─ TLS 1.3 → upstream:443 → TLS term :4443 → mtg :2083
            └─ plain HTTP CONNECT → fallback Squid :3128

Squid access → cache_peer upstream:proxy_port
            ├─ squid_transit_tls=true → TLS с проверкой имени transit.internal
            └─ squid_transit_tls=false → HTTP CONNECT без TLS участка
```

HTTPS-вход и шифрование участка включаются независимо и явно; оба по умолчанию
выключены. Порт 443 сам по себе не означает HTTPS-прокси. TLS целевого сайта
внутри CONNECT остаётся сквозным между клиентом и сайтом.

### Upstream nodes

За nginx внешний порт `proxy_port` равен 443. В отличие от локальных портов,
этот порт фиксирован контрактом совместного размещения. Preflight проверяет его
до установки пакетов; `squid_local_port` согласованно меняет fallback и назначения
локальных терминаторов. Порты всех включённых слушателей должны различаться.

```text
Access → upstream nginx:443 (ssl_preread + PROXY protocol)
            ├─ SNI=transit.internal → Squid TLS term :4444 → Squid :3128
            ├─ SNI=max.ru / tgproxy.example.com → MTProxy TLS term :4443 → mtg :2083
            └─ plain HTTP CONNECT → fallback Squid :3128
Squid upstream → целевой сайт
```

Squid TLS-терминатор работает и с выключенным MTProxy. Он разрешает соединения
только с адресов access, но заново создаёт PROXY-заголовок от loopback:
исходный клиентский IP намеренно не восстанавливается. На access IP клиента
восстанавливается для локальной проверки доступа и журналирования.

При `behind_nginx: false` и выключенном MTProxy прямой Squid принимает
`proxy_port` самостоятельно: HTTP при выключенном transit TLS, HTTPS при включённом.
Этот режим требует свободного внешнего порта; общий nginx на нём не используется.

Для двух IP одного HTTPS-имени на access используются отдельные HTTP-01 vhost на
80/tcp. Локальный токен имеет приоритет, отсутствующий запрашивается у соседа с
ограничением одного перехода. Каждый access самостоятельно выпускает и продлевает
свой сертификат; приватные ключи между узлами не копируются.

**Таймауты:** Squid — `read_timeout` (по умолчанию час простоя), router и
Squid/HTTPS-терминаторы — не менее 3900 секунд; MTProxy relay/терминатор —
360 секунд при пределе простоя mtg 300 секунд. TCP keepalive включён.

### Upstream прокси (Squid cache_peer)

Access прокси автоматически переключается между upstream серверами. Upstream определяются как хосты группы `upstreams` в inventory:

```yaml
# inventory.yml
upstreams:
  hosts:
    upstream-01:
      ansible_host: 198.51.100.11
  vars:
    proxy_port: 443
```

Параметры failover:
- `userhash` — выбор пира по хэшу имени пользователя (устойчивая привязка); единственный заданный алгоритм, при отказе пира кольцо перестраивается среди живых
- `connect-fail-limit=2` — после 2 неудач сервер помечается недоступным
- `connect-timeout=5` — таймаут подключения 5 секунд
- `dead_peer_timeout=15` — проверка недоступных серверов каждые 15 секунд

## Отказоустойчивость

### Виртуальный IP для access (Keepalived)

Access-узлы могут делить единый виртуальный адрес по VRRP. Возможность необязательная: признак `enable_keepalived` по умолчанию выключен, и без него клиент обращается к конкретному узлу.

```yaml
# Настройки в inventory.yml (группа access_proxies → vars)
enable_keepalived: true              # По умолчанию false
keepalived_vip: 192.168.0.2         # Виртуальный IP для клиентов (обязательно задать)
# keepalived_interface: eth0        # Автоопределение через ansible_default_ipv4.interface
keepalived_vrid: 51
keepalived_auth_pass: "<your-password>"

# Для каждого хоста
access01.example.com:
  keepalived_state: MASTER
  keepalived_priority: 100
access02.example.com:
  keepalived_state: BACKUP
  keepalived_priority: 90
```

### CrowdSec IPS

**CrowdSec** — современная система предотвращения вторжений (IPS) с автоматическим обновлением threat intelligence фидов от глобального сообщества (70k+ серверов).

**Функции:**
- Защита от SSH brute-force атак
- Обнаружение HTTP-сканеров по поддерживаемым nginx-источникам; метка Squid `squid` пока не имеет штатного парсера
- Автоматическая блокировка через firewall bouncer (nftables)
- Whitelist легитимных актёров (Google, Microsoft, Cloudflare)
- **Whitelist инфраструктурных IP** — все access и upstream ноды автоматически добавляются в whitelist для предотвращения самоблокировки

**Управление:**

```bash
# Включение/отключение в inventory.yml
crowdsec_enabled: true  # или false

# Развернуть только CrowdSec
ansible-playbook -i inventory.yml playbook.yml -t crowdsec

# Проверить статус на хосте
ssh root@<host> 'systemctl status crowdsec crowdsec-firewall-bouncer'

# Просмотреть активные блокировки
ssh root@<host> 'cscli decisions list'

# Просмотреть логи
ssh root@<host> 'journalctl -u crowdsec -f'

# Удалить блокировку IP (если ошибочно заблокирован)
ssh root@<host> 'cscli decisions delete --ip 1.2.3.4'
```

**Потребление ресурсов:**

- CrowdSec: бюджет автоматически из общего плана, минимум 192 МиБ
- Firewall bouncer: бюджет автоматически из общего плана, минимум 24 МиБ
- Диск: ~50 MB (collections + база решений)

### MTProxy (Telegram Proxy)

**MTProxy** — прокси-сервер для обхода блокировок Telegram через fake-TLS маскировку.

**Архитектура:**
- **Upstream nodes**: mtg daemon на порту 2083, за nginx TLS 1.3 терминатором (:4443)
- **Access nodes**: nginx stream SNI-роутинг на порту 443, TLS 1.3 relay к upstream

**Функции:**
- DPI-circumvention через fake-TLS домен (`max.ru`)
- TLS 1.3 шифрование access→upstream transit (self-signed cert, `proxy_ssl`)
- Load balancing между upstream instances (round-robin)
- Firewall защита: доступ к MTProxy только от access nodes
- PROXY protocol переносит адрес access-узла для проверки доступа к upstream-терминатору. К mtg заголовок не передаётся: исходный IP клиента намеренно скрыт, mtg видит локальное соединение
- Интеграция с Squid: nginx на access маршрутизирует MTProxy трафик на upstream:443, остальной — на локальный Squid (127.0.0.1:3128)

**Управление:**

```bash
# Включение/отключение в inventory.yml
mtproxy_enabled: true  # или false

# Развернуть только MTProxy (upstream + access)
ansible-playbook -i inventory.yml playbook.yml -t mtproxy

# Развернуть только nginx для MTProxy (access)
ansible-playbook -i inventory.yml playbook.yml -t nginx

# Проверить статус на upstream хосте
ssh root@<upstream-host> 'systemctl status mtg'

# Проверить статус nginx на access хосте
ssh root@<access-host> 'systemctl status nginx'

# Просмотреть активные подключения к MTProxy
ssh root@<upstream-host> 'ss -tnp | grep :2083'

# Получить секрет для подключения клиентов
ssh root@<upstream-host> 'grep "^secret" /etc/mtproxy/mtg.toml'
```

**Конфигурация клиента:**

Подключиться к MTProxy:
- **Сервер**: IP одной из access nodes (или VIP, если Keepalived включён)
  - access01.example.com: `203.0.113.1`
  - access02.example.com: `203.0.113.2`
- **Порт**: `443`
- **Секрет**: получить из `/etc/mtproxy/mtg.toml` на любом upstream node

Формат ссылки для Telegram:
```
tg://proxy?server=203.0.113.1&port=443&secret=<hex-секрет>
```

**Потребление ресурсов:**
- **MTProxy (upstream)**: бюджет рассчитывается автоматически, минимум 32 МиБ; число сессий ограничивается памятью и дескрипторами
- **nginx stream (access)**: минимальное (включено в общий nginx budget)

**Переменные (inventory.yml):**

Значения — в общей таблице [«Переменные»](#переменные) выше; здесь не дублируются,
чтобы не расходились при правке.

## Совместное развёртывание с Matrix

ai-proxy владеет общим nginx, SNI router на 443, бюджетом общего процесса nginx,
CrowdSec/bouncer и интеграцией firewall. Соседний Matrix добавляет файлы под своим
префиксом и собственные правила; его конфиги ai-proxy не переписывает.

```text
Internet → nginx:443 (общий SNI router)
             ├─ proxy.example.com → HTTPS term :4445 → Squid :3128 → upstream:443
             ├─ max.ru → MTProxy relay :9443 → upstream:443
             ├─ matrix.example.com → обработчик Matrix на loopback
             └─ plain HTTP CONNECT → Squid :squid_local_port → upstream:proxy_port

CrowdSec ← собственные acquis.d-файлы каждого проекта
Firewall ← правила ai-proxy + контракт общих портов Matrix
```

| Объект | Владелец и изменение |
|---|---|
| `nginx.conf`, `stream.d/00-sni-router.conf` | ai-proxy поддерживает общие worker/include и перезаписывает свой router; сосед добавляет собственные фрагменты |
| `stream.d/sni-map.d/*.conf`, `stream.d/*.conf`, `conf.d/*.conf` | Каждый проект управляет собственными файлами; имя SNI должно быть уникальным |
| CrowdSec/bouncer | ai-proxy задаёт общий бюджет и службы; источники журналов разделены по `acquis.d/` |
| UFW | Настраиваются отдельные правила и политики; полного reset нет |
| nftables | Заменяются только управляемые цепочки и наборы внутри общей таблицы; таблицы CrowdSec и чужие объекты сохраняются |
| iptables/ip6tables | Собственные цепочки и восстановление с `--noflush`; остальные правила сохраняются |
| Порты Matrix | Сосед публикует контракт в `/etc/shared-host/`; ai-proxy применяет его в действующий backend |

Состав файлов для расширенного TLS-сценария:

```text
# Access: /etc/nginx/
conf.d/aiproxy-https-acme.conf             # HTTP-01, включая второй access
stream.d/00-sni-router.conf               # Общий слушатель 443
stream.d/10-aiproxy-capacity.conf          # Зона лимита транзитных сессий
stream.d/10-aiproxy-upstreams.conf         # MTProxy relay
stream.d/11-aiproxy-https-proxy.conf       # HTTPS term :4445
stream.d/sni-map.d/aiproxy.conf           # MTProxy
stream.d/sni-map.d/aiproxy-https-proxy.conf
stream.d/sni-map.d/<префикс-Matrix>.conf   # Принадлежит соседу

# Upstream: /etc/nginx/
stream.d/00-sni-router.conf
stream.d/10-aiproxy-capacity.conf
stream.d/10-mtproxy-tls.conf               # Только при включённом MTProxy
stream.d/20-squid-tls-term.conf            # При включённом Squid transit TLS
stream.d/sni-map.d/mtproxy.conf            # Только при включённом MTProxy
stream.d/sni-map.d/squid.conf              # При включённом Squid transit TLS
```

Список показывает условные компоненты: выключенные HTTPS, ACME, MTProxy или transit
TLS не требуют соответствующих файлов. Общий router сам TLS не завершает;
это делают отдельные локальные терминаторы. Перечитывание nginx выполняется
без общего принудительного завершения старых worker и без разрыва чужих сессий.
