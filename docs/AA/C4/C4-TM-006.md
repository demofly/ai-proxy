## Описание

Файл `Servers/deploy/templates/iptables-upstream.rules.j2` (50 строк) -- Jinja2-шаблон набора правил iptables для upstream-узлов, на которых **не** применяется ни nftables (не Debian), ни UFW (ufw неактивен): Ubuntu после чистой установки и RHEL-семейство. Генерирует `/etc/iptables/aiproxy-upstream.rules` в формате `iptables-restore`. Объявляет **единственную** цепочку `SQUID-PROXY` и закрывает те же порты, что nftables-вариант: Squid (`squid_port`), MTProxy 443 (условно), DNS 53/tcp+udp -- всё только с IP access-прокси.

## Структура файла

| Секция | Описание |
|---|---|
| **Заголовок** | Комментарии: способ применения, запрет объявлять встроенные цепочки, ссылка на юнит восстановления |
| `*filter` / `:SQUID-PROXY - [0:0]` | Объявление таблицы и **только своей** цепочки |
| Loopback | `-i lo -j RETURN` -- до всех запретов |
| Squid | `-s {access_ip} -p tcp --dport {squid_port} -j ACCEPT` на каждый access-узел |
| MTProxy | то же для порта 443 при `mtproxy_enabled` |
| DNS | `-s {client} -p {tcp,udp} --dport 53 -j ACCEPT` на каждый IP из `dns_allowed_clients` |
| Запреты | `--dport {squid_port}`, `--dport 53` (tcp и udp) -- `DROP` |
| Хвост | `-j RETURN` -- решение по остальному трафику принимает INPUT |
| `COMMIT` | Завершение транзакции |

## Ключевые механизмы

### Атомарное применение только своей цепочки

```
iptables-restore --noflush /etc/iptables/aiproxy-upstream.rules
```

`--noflush` не очищает таблицу целиком; объявленная в файле цепочка заменяется полностью и **одной транзакцией**. Отсюда два свойства:

1. **Нет окна открытого порта.** Прежний способ (`iptables -F SQUID-PROXY` и добавление правил по одному) оставлял цепочку пустой на время добавления: при политике INPUT `ACCEPT` порт 53 в этот момент открыт всем, и так на каждом прогоне плейбука.
2. **Co-deployment сохраняется.** Цепочки других проектов (Matrix) и правила встроенных цепочек не затрагиваются -- `--noflush` меняет только то, что объявлено в файле. Поэтому шаблон **не должен** объявлять `INPUT`/`FORWARD`/`OUTPUT`: их объявление очистило бы чужие правила. Переход из INPUT в `SQUID-PROXY` создаётся отдельной идемпотентной задачей, а не из этого файла.

Проверено на стенде: после применения файла с одной объявленной цепочкой прежнее правило в `SQUID-PROXY` заменено, а чужая цепочка `MATRIX-FW` и оба перехода в `INPUT` сохранены без изменений.

### Проверка до применения

Задача деплоя шаблона использует `validate: iptables-restore --test %s`: файл разбирается и правила конструируются без записи в ядро. Синтаксическая ошибка останавливает развёртывание до того, как затронуты действующие правила.

### Определение изменения

Применение сравнивает `iptables -S SQUID-PROXY` до и после: команда выполняется всегда (это дёшево и атомарно), но `changed` докладывается, только если цепочка действительно изменилась. Иначе каждый прогон плейбука отмечался бы как изменение и скрывал настоящие расхождения.

### Восстановление при загрузке

Восстанавливается **только собственная цепочка и ссылка на неё**, а не сохранённый набор
правил целиком. Полное восстановление здесь запрещено правилом совместного размещения:
снимок, снятый на узле с соседом, содержит и его правила, и возвращая такой снимок,
проект распоряжался бы чужими правилами — в том числе возвращая снятые соседом намеренно.


Юнит `aiproxy-firewall.service` (oneshot, `Before=network-pre.target`) повторяет то же применение плюс проверку перехода из INPUT. Пакеты `iptables-persistent` / `iptables-services` намеренно **не** используются: они восстанавливают снимок всего ruleset и тем самым откатывали бы правила co-deployment проектов к состоянию на момент нашего развёртывания.

## Переменные

| Переменная | Тип | Значение по умолчанию | Описание |
|---|---|---|---|
| `squid_chain` | string | `SQUID-PROXY` | Имя собственной цепочки (задаётся в блоке задач) |
| `squid_port` | int | -- | Порт Squid для whitelist |
| `groups['access_proxies']` | list | -- | Список access-прокси хостов |
| `dns_allowed_clients` | list | -- | Клиенты DNS: IP access-прокси + `dns_extra_clients` |
| `mtproxy_enabled` | bool | false | Включение правил для MTProxy port 443 |

## Критерии приёмки

| # | Критерий | Метрика / Способ проверки | Целевое значение |
|---|----------|---------------------------|------------------|
| 1 | Файл разбирается | `iptables-restore --test <файл>` | exit 0 |
| 2 | Цепочка применена | `iptables -S SQUID-PROXY` | правила соответствуют шаблону |
| 3 | Переход из INPUT существует | `iptables -C INPUT -j SQUID-PROXY` | exit 0 |
| 4 | Чужие цепочки сохранены | `iptables -S` до и после применения | правила других проектов не изменились |
| 5 | Повторный прогон не меняет состояние | второй запуск плейбука | задача применения -- `ok`, не `changed` |
| 6 | DNS доступен только access-нодам | `dig` и `dig +tcp` с access-ноды и со стороннего хоста | NOERROR и timeout соответственно |
| 7 | Правила переживают перезагрузку | reboot, затем критерии 2--3 | состояние не изменилось |

## Доказательство реализации

### Конструктивное

Шаблон описывает целевое состояние цепочки декларативно, одним файлом; применение и восстановление при загрузке используют один и тот же файл, поэтому состояние после перезагрузки совпадает с состоянием после развёртывания по построению.

### Эмпирическое

- `iptables -S SQUID-PROXY` после применения
- `iptables -vnL SQUID-PROXY` -- счётчики на запрещающих правилах после попытки со стороннего хоста
- Проверка сохранности чужой цепочки: `iptables -S MATRIX-FW` до и после

### Негативное

- **Окно открытого порта при обновлении правил** -- одна транзакция вместо flush + пошаговое добавление
- **Снятие правил co-deployment проектов** -- объявляется только собственная цепочка; встроенные не объявляются никогда
- **Откат чужих правил при загрузке** -- восстанавливается только своя цепочка, полный снимок ruleset не используется
- **Разрыв локального резолвинга** -- `-i lo -j RETURN` выше запретов
- **Ошибка в шаблоне** -- `iptables-restore --test` до применения
