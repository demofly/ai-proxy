# C4-PB-002 -- Инвентори (inventory.yml)

**Последняя правка AI:** 2026-10-19

## Ссылки

- Родительские требования C3: [C3-AD-001](../C3/C3-AD-001.md)
- Связанные C4: [C4-PB-001](C4-PB-001.md) (плейбук, потребитель переменных)

## Описание

Ansible inventory определяет топологию инфраструктуры AI Assistants Proxy: группы хостов, их роли, адреса и полный набор конфигурационных переменных. Отслеживается образец `Servers/deploy/inventory.yml.sample`; рабочий `inventory.yml` создаётся из него локально и в контроль версий не попадает. Значения ниже приведены по образцу.

## Структура файла

| Секция | Описание |
|---|---|
| **all.children.access_proxies** | Группа access-прокси (2 хоста: access-01, access-02) с per-host переменными Keepalived (state, priority) |
| **access_proxies.vars** | Переменные группы: proxy_role=access, proxy_port=443, enable_auth/logging/caching, behind_nginx, Keepalived-настройки |
| **all.children.upstreams** | Группа upstream-прокси (2 хоста: upstream-01, upstream-02) |
| **upstreams.vars** | Переменные группы: proxy_role=upstream, proxy_port=443, behind_nginx, без аутентификации/логирования/кеширования |
| **all.vars** | Глобальные переменные: ansible_user, python interpreter, read_timeout, CrowdSec, MTProxy, DNS, allowed_domains, allowed_domain_patterns |

## Ключевые механизмы

### Двухуровневая иерархия хостов

Инвентори организован в две группы с разными ролями:

- **access_proxies**: клиентские точки входа с аутентификацией, кешированием, Keepalived VIP
- **upstreams**: анонимные транспортные узлы с firewall, MTProxy

Переменная `proxy_role` определяет поведение плейбука для каждой группы.

### Управление секретами и изоляция от контроля версий

Рабочий инвентори содержит действительные реквизиты доступа и потому **раскрытию не подлежит**:

- `keepalived_auth_pass` -- пароль VRRP-аутентификации
- `mtproxy_secret` -- hex-секрет MTProxy (Fake-TLS)
- IP-адреса узлов

Отсюда раскладка артефактов (решение владельца от 2026-08-28):

| Файл | Контроль версий | Содержимое |
|---|---|---|
| `Servers/deploy/inventory.yml` | исключён (`.gitignore`) | действительные адреса и реквизиты; создаётся локально копированием образца |
| `Servers/deploy/inventory.yml.sample` | отслеживается | та же структура, адреса из документационных диапазонов (RFC 5737), значения реквизитов пустые либо помечены как задаваемые локально |
| `Servers/deploy/passwd` | исключён (`.gitignore`) | хеши паролей пользователей Squid -- тоже реквизиты доступа, а не пример |
| `Servers/deploy/passwd.example` | отслеживается | формат и команда генерации без единой действительной записи |

Основание: отправка в удалённый репозиторий есть раскрытие неопределённому кругу лиц — доступ имеют администраторы службы, зеркала, резервные копии и всякий будущий участник, — и перезапись истории его не отменяет. В отслеживаемых артефактах остаются имена ключей и указатель на источник значения, но не значения.

### Domain whitelist

Два механизма фильтрации доменов:

1. **allowed_domains** -- явный список доменов (dashscope.aliyuncs.com, copilot-proxy.githubusercontent.com и др.)
2. **allowed_domain_patterns** -- regex-паттерны для групп доменов (\.ai$, OpenAI, Anthropic, Google Gemini, GitHub Copilot, Microsoft/Azure, Cursor AI, DeepL)

## Переключатели и их действие

Что именно меняется при включении каждого — установлено по коду, а не по назначению
переменной:

| Переключатель | Где читается | Что меняется |
|---|---|---|
| `enable_auth` | Шаблон Squid | Выпускаются проверка подлинности и разрешающее правило. При выключении разрешающего правила нет вовсе, и доступ закрыт целиком |
| `enable_logging` | Шаблон Squid, роль обнаружения | Журнал обращений ведётся либо отключается; от него же зависит, попадёт ли журнал в источники обнаружения |
| `enable_caching` | Шаблон Squid | Появляется дисковый кеш либо запрет кеширования. Память под кеш объектов на access-узле задаётся **независимо** от переключателя |
| `behind_nginx` | Плейбук, через `nginx_on_443` | Определяет, слушает ли Squid петлевой адрес за маршрутизатором или внешний порт напрямую |
| `crowdsec_enabled` | Плейбук | Подключает роль обнаружения и включает её долю в расчёт памяти |
| `mtproxy_enabled` | Плейбук, роли | Разворачивает MTProxy и маршрутизатор на upstream-узле. **Задан глобально**, поэтому влияет и на access-узлы: входит в вычисление работы за маршрутизатором, и его включённость означает там «маршрутизатор нужен», хотя сам MTProxy на access не разворачивается |
| `enable_keepalived` | Плейбук | Разворачивает переключение виртуального адреса на access-узлах |
| `dns_resolver_dnssec` | Шаблон резолвера | Выпускает ключ доверия; проверка подписей обеспечена и установкой пакета корневых данных, и инициализацией ключа |
| `dns_resolver_prefetch` | Шаблон резолвера | Обновление популярных записей до истечения срока |
| `allow_direct_fallback` | Шаблон Squid | Управляет выпуском запрета прямых обращений: `false` (умолчание) — выпускается `never_direct allow all`, прямой выход невозможен; `true` — запрет не выпускается, при отказе всех вышестоящих узлов обращение уходит напрямую, раскрывая адрес узла целевому сервису |

Последняя строка — причина, по которой таблица заведена: перечень переменных
с умолчаниями существовал и прежде, но не отвечал на вопрос, что именно изменится.

### Осмотр распознаёт существующее, но не создаёт

Работа за маршрутизатором вычисляется из трёх источников: явного переопределения,
включённости MTProxy и осмотра узла. Осмотр отвечает на вопрос «работает ли уже
маршрутизатор с прослушиванием порта 443» — то есть распознаёт **существующее
состояние**, а на чистом узле даёт отрицательный ответ.

Отсюда следствие, которое стоит держать в уме при заведении нового access-узла: если
переопределение не задать и выключить MTProxy глобально, вычисление даст «маршрутизатора
нет», и Squid займёт внешний порт напрямую. Это допустимый режим, описанный
в руководстве, но получить его случайно легче, чем кажется.

Нынешняя установка до этого не доходит: признак MTProxy включён глобально,
а переопределение задано явно в обеих группах.

## Доказательство реализации

### Конструктивное

Инвентори определяет двухуровневую топологию (access + upstream) с чётким разделением ответственности. Переменные разнесены по трём уровням (per-host, group, global), обеспечивая переопределение через стандартный механизм приоритетов Ansible.

### Эмпирическое

- Валидация: `ansible-inventory -i inventory.yml --list`
- Доступность хостов: `ansible all -i inventory.yml -m ping`
- Проверка переменных: `ansible all -i inventory.yml -m debug -a "var=proxy_role"`

### Негативное

- **Чувствительные данные** -- рабочий инвентори исключён из контроля версий, в репозитории остаётся образец без значений; внутри самого файла значения хранятся открытым текстом. Решением владельца (2026-08-29) это признано достаточной мерой: защищённое хранилище добавило бы пароль при каждом прогоне, не меняя модели угроз — доступ к управляющей машине даёт и то и другое
- **Hardcoded IP** -- IP-адреса зафиксированы; изменение инфраструктуры требует обновления инвентори
- **Keepalived выключен в образце** -- `enable_keepalived: false`; при включении требуется задать `keepalived_vip`, иначе задачи роли пропускаются
