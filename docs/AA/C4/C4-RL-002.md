# C4-RL-002 -- Роль nginx (roles/nginx/)

**Последняя правка AI:** 2026-10-19

## Ссылки

- Родительские требования C3: [C3-NX-001](../C3/C3-NX-001.md)
- Связанные C4: [C4-PB-001](C4-PB-001.md), [C4-PB-002](C4-PB-002.md), [C4-TM-001](C4-TM-001.md), [C4-RL-003](C4-RL-003.md)

## Описание

`Servers/deploy/roles/nginx/` управляет общим nginx на access: маршрутизатором
SNI на публичном 443, локальным Squid за PROXY protocol и необязательным клиентским
HTTPS-прокси. TLS сайта внутри CONNECT остаётся сквозным; внешнее TLS-соединение
с HTTPS-прокси завершается в отдельном loopback-сервере nginx.

## Совместное размещение

ai-proxy владеет `nginx.conf`, общим маршрутизатором и пределами nginx. Соседние
проекты добавляют собственные фрагменты в `stream.d/`, `stream.d/sni-map.d/`,
`stream.d/router.d/` и `conf.d/`. Общий router обновляется при каждом развёртывании;
`force: no` не применяется. Файлы соседей не переписываются.

Router выполняет ssl_preread, выбирает SNI-цель и передаёт PROXY-заголовок.
Открытый HTTP CONNECT попадает в `fallback_squid` на 127.0.0.1:3128. TLS с неизвестным
SNI также попадёт в этот plaintext fallback и не является корректным HTTPS-входом.
Поэтому клиентскому HTTPS-прокси нужны отдельное имя и доверенный сертификат.

## Клиентский HTTPS и сертификаты

По умолчанию `https_proxy_enabled=false`. Включение требует access,
`enable_auth=true`, отдельного имени и свободного loopback-порта (4445 по умолчанию).
SNI-конфликт проверяется до ACME, сертификат — через `openssl verify -verify_hostname`,
ключ и конфигурация — через `nginx -t`. Ошибочные фрагменты восстанавливаются либо
удаляются до reload. Штатный пароль проверяет существующий Squid.

`set_real_ip_from 127.0.0.1` применяется только в клиентском терминаторе access;
управление анонимностью upstream в эту роль не переносится. Ограничитель использует
общую зону `aiproxy_transit`; расчёт соединений предусматривает четыре nginx-слота
на туннель. MemoryMax служб и проекта из-за HTTPS не увеличиваются.

`https_proxy_acme_enabled=true` включает Certbot webroot. Общее имя может иметь
два IP: все A/AAAA должны вести на подготовленные access с открытым 80/tcp.
Участники обнаруживаются по одинаковому имени и включённым HTTPS/ACME в inventory.
Отсутствующий локально токен запрашивается по IP соседа; заголовок hop запрещает
дальнейшую пересылку. Ключи и сертификаты остаются собственными на каждом узле.
Ответы не кешируются, GET/HEAD ограничены путём HTTP-01. Собственный именной HTTP-сайт не
меняет default_server соседей. Deploy-hook выполняет `nginx -t` и reload после
продления. При первом запуске `strategy: linear` подготавливает все HTTP-сайты до
выпуска сертификата. Узел без сертификата проверяет обратный путь токена через
каждого соседа; пробный файл удаляется и при ошибке. Последующие продления не
требуют Ansible. Опциональный `https_proxy_acme_address` отделяет HTTP-адрес от SSH;
допустим только IP, не общее DNS-имя. Если сертификат сопровождает другая система,
ACME выключен у всех участников имени, пути к полной
цепочке и ключу задаются явно. Все параметры и их умолчания описаны в
[образце инвентори](../../../Servers/deploy/inventory.yml.sample) и
[инструкции](../../../Servers/deploy/README.md#https-прокси-для-клиентов).

## Миграция Squid

При переводе Squid с публичного 443 сохраняется резервная конфигурация, новый
конфиг проверяется `squid -k parse`, nginx — через `nginx -t` до остановки Squid.
Squid останавливается только если занимает 443; затем запускается nginx и проверяется его порт. Основной плейбук
позже применяет параметры Squid подходящим reload/restart. Ошибка миграции вызывает
восстановление прежнего Squid. HTTPS и ACME настраиваются после этого блока;
ошибка их настройки не вызывает перезапуск уже работающего Squid.

## Критерии приёмки

| # | Критерий | Способ проверки | Целевое значение |
|---|---|---|---|
| 1 | Общий nginx работает | `nginx -t`, `systemctl is-active nginx` | Успех, active |
| 2 | Прежний HTTP-вход сохранён | HTTP CONNECT через 443 | Полная передача тела |
| 3 | HTTPS требует пароль | CONNECT без credentials | 407 |
| 4 | HTTPS проверяет подлинность | Клиент с публичным trust store | Сертификаты прокси и сайта приняты |
| 5 | Сохраняются протокол и данные | Настоящий nginx в изолированном fixture | ALPN HTTP/1.1, блоки 1–65536 байт без потерь, исходный адрес access-клиента |
| 6 | Ошибочная конфигурация откатывается | Тест с отсутствующим ключом, прежними/новыми фрагментами | Прежние файлы восстановлены, новые удалены, reload не вызван |
| 7 | Чужой локальный listener защищён | Тест занятого порта | Отказ до замены фрагментов |
| 8 | Продление работает | `certbot renew --cert-name <имя> --dry-run --run-deploy-hooks` | Успех HTTP-01 и reload |
| 9 | HTTP-01 работает через оба IP | Два nginx, независимые webroot, одновременные токены | Каждый токен доступен через оба адреса; отсутствующий даёт 404 без цикла |

## Доказательства

`Servers/deploy/tests/test_https_proxy.py` запускает реальные шаблоны через Ansible,
nginx на случайных loopback-портах и транзакцию отката. Нативные тесты включаются
переменными AIPROXY_TEST_NGINX и AIPROXY_TEST_NGINX_STREAM; они не являются нагрузочными.
Рабочие измерения приведены в [аудите соединений](../../../Servers/deploy/connection-audit.md).
`Servers/deploy/tests/test_acme_cluster.py` проверяет состав участников и реальную
пересылку HTTP-01 между двумя nginx, удаление токенов, GET/HEAD и чужой HTTP-сайт.
