## Описание

Файл `Servers/deploy/templates/squid-access.conf.j2` (379 строк) -- Jinja2-шаблон конфигурации Squid для access-прокси. Генерирует `/etc/squid/squid.conf` на access-узлах. Обеспечивает аутентификацию клиентов, domain whitelist, маршрутизацию через upstream peers с балансировкой, разграничение пиров по пулам пользователей, анонимизацию запросов и адаптивную настройку производительности.

## Ключевые механизмы

### Аутентификация (условная)

При `enable_auth: true`:

- Программа: `/usr/lib/squid/basic_ncsa_auth` с файлом паролей `/etc/squid/passwd`
- 5 дочерних процессов (startup=5, idle=1)
- TTL кредов: 2 часа, case-sensitive
- ACL `authenticated proxy_auth REQUIRED`

При `enable_auth: false` ACL `authenticated` не определяется, **и разрешающие правила не выпускаются вовсе**: остаётся единственное правило `http_access deny all`, то есть отклоняется любой запрос (fail-closed, решение владельца от 2026-08-28). Доступ без проверки подлинности на access-уровне не предоставляется ни к каким доменам.

Прежняя редакция выпускала `http_access allow authenticated` безусловно, из-за чего при `enable_auth: false` Squid отвергал конфигурацию целиком (`ERROR: ACL not found: authenticated`) и развёртывание access-узла обрывалось. Проверено на стенде: конфигурация проходит `squid -k parse`, запрос через прокси получает 403.

### Domain whitelist (двойной)

Два взаимодополняющих механизма фильтрации:

1. **allowed_domains** -- `acl allowed_domains dstdomain {domain}` для каждого домена из списка
2. **allowed_domain_patterns** -- `acl allowed_domain_regexp dstdom_regex -i {pattern}` для regex-паттернов

Оба ACL используются в правилах доступа: `http_access allow authenticated allowed_domains` и `http_access allow authenticated allowed_domain_regexp`.

### Upstream peers (userhash балансировка)

Для каждого upstream, входящего хотя бы в один активный пул (раздел «Пулы пользователей» ниже), в порядке группы inventory `upstreams`:

```text
cache_peer {ip} parent {port} 0 no-query userhash connect-fail-limit=2 connect-timeout=5 name={host}
```

- **userhash** -- устойчивая привязка пользователя к пиру по хешу его имени, директива `sourcehash` в шаблоне не выпускается
- **connect-fail-limit=2** -- после 2 неудач peer помечается мёртвым
- **dead_peer_timeout=15s** -- проверка мёртвых peers каждые 15 секунд
- **never_direct allow all** -- весь трафик через upstream, пока `allow_direct_fallback` выключен
- **nonhierarchical_direct off** -- выпускается вместо запрета при `allow_direct_fallback: true`. По умолчанию Squid отправляет запросы `CONNECT`, то есть весь HTTPS, напрямую в обход пиров, и без этой директивы включённый признак выводил бы основной поток мимо upstream и мимо разграничения пулов. Дефект существовал и до введения пулов

### Пулы пользователей

Реализует требование [C2-FR-009](../C2/C2-FR-009.md) через компонент [C3-SA-001](../C3/C3-SA-001.md), решение — [ADR-000010](../ADR/ADR-000010.md). Шаблон получает разрешённые пулы в переменной `_squid_pools`: её вычисляет плейбук фильтром `aiproxy_pools` ([C4-PB-001](C4-PB-001.md)). Элемент — `{name, all_users, users, upstreams}`, где `upstreams` уже упорядочены по группе inventory `upstreams`. Прямой рендер без этой переменной останавливается ошибкой: иначе он молча дал бы конфигурацию «отказ всем».

1. **Отбор активных пулов.** Активен пул, у которого есть и upstream, и пользователи (`all_users` либо непустой `users`). Пулы без upstream или без пользователей не порождают ни ACL, ни пиров.
2. **Перечень пиров** -- упорядоченное уникальное объединение upstream активных пулов. `cache_peer` объявляется только для них.
3. **ACL пулов** (только при `enable_auth: true`). На каждый активный пул выпускается `acl aiproxy_pool_<имя> proxy_auth`: для группы `all` -- `REQUIRED`, иначе имена пользователей по 20 в строке. Строки с одним именем ACL Squid объединяет по ИЛИ, поэтому длинный список дробится без потери смысла.
4. **Объединённый ACL** `aiproxy_routed` -- `REQUIRED`, если хотя бы один активный пул охватывает всех, иначе отсортированное объединение пользователей активных пулов.
5. **Доступ к пиру.** На каждый пир -- строки `cache_peer_access <пир> allow aiproxy_pool_<имя>` для каждого активного пула, куда он входит, и завершающая `cache_peer_access <пир> deny all`. `userhash` выбирает пира только среди разрешённых, это подтверждено нативной проверкой.
6. **Отказ при пустом наборе.** Первым правилом доступа после правил менеджера выпускается `http_access deny authenticated !aiproxy_routed all`. Пользователь вне активных пулов получает HTTP 403 независимо от `allow_direct_fallback`. Завершающий `all` не даёт Squid отвечать перезапросом 407, когда последний ACL строки -- `proxy_auth`. Если активных пулов нет вовсе, выпускается `http_access deny all`.

При `enable_auth: false` ACL пулов и `cache_peer_access` не выпускаются: имени пользователя нет, и все пиры перечня доступны всем запросам. Сами запросы при этом отклоняются политикой fail-closed (раздел «Аутентификация» выше).

### Анонимизация и маскировка под браузер

Заголовки запроса `CONNECT` приводятся к виду обращения браузера Chrome с Windows:


- Удаление: X-Forwarded-For, X-Real-IP, Via, X-Cache, Server
- Замена User-Agent на постоянную строку браузера Chrome. Действует на заголовках запроса установления туннеля, то есть при **всяком** обращении; заголовки внутри установленного туннеля зашифрованы, и прокси их не видит и не правит
- Добавление: Accept, Accept-Language, Accept-Encoding, Sec-Fetch-*, Sec-Ch-Ua, DNT, Cache-Control

**Где эта маскировка действует, а где нет.** Заголовки правятся у запроса `CONNECT` —
той оболочки, которой access-узел просит upstream открыть туннель. Их видит наблюдатель
на участке от клиента до upstream-узла. Внутри туннеля идёт сквозной TLS между клиентом
и целевым сервисом: его свойства — набор шифров, расширения, отпечаток библиотеки клиента —
проходят насквозь, и прокси их не меняет. Целевой сервис видит подлинные свойства клиента
и подлинный `User-Agent` приложения; от него скрыт только адрес клиента.

### Предел времени жизни соединения

Помимо времени ожидания данных действует предел, ограничивающий сеанс целиком:

| Величина | Значение | Что ограничивает |
|---|---|---|
| `read_timeout` — простой туннеля | 1 час | Паузу без передачи данных в обе стороны; таймер переармируется каждой порцией |
| `client_lifetime` — жизнь соединения | 1 сутки | Сеанс целиком, независимо от активности |
| `client_idle_pconn_timeout` | 60 секунд | Удержание неиспользуемого постоянного соединения |
| `request_timeout` | 30 секунд | Паузу до получения запроса |
| `connect_timeout` | 15 секунд | Установление соединения с вышестоящим узлом |

Различие первых двух задаёт инвариант: предел жизни обязан быть строго БОЛЬШЕ предела
простоя, иначе рвать соединение будет он, и предел простоя перестанет что-либо значить —
активный туннель погибнет наравне с бездействующим. Отсюда сутки против часа: обмен,
по которому идут данные, живёт до суток, бездействующий закрывается через час.

### Граница действия анонимизации

Различать следует два набора заголовков, и от смешения их происходит большинство неверных
оценок этого механизма:

| Набор | Виден прокси | На него действуют директивы | Кто его получает |
|---|---|---|---|
| Заголовки запроса `CONNECT` | Да: идут открыто до установления туннеля | Да | Вышестоящий прокси и всякий, кто наблюдает участок до него |
| Заголовки внутри туннеля | Нет: зашифрованы вместе с обменом | Нет | Целевой сервис |

Отсюда два вывода, которые не следует подменять один другим.

**Директивы работают** — и в целевом сценарии тоже: обращения к API идут запросами
`CONNECT`, их заголовки прокси видит и правит, снимая пересылаемый адрес клиента
и признаки прохождения через прокси.

**Целевой сервис их не видит.** Он получает заголовки изнутри туннеля — подлинные,
вместе с набором шифров и отпечатком библиотеки клиента. Подмена строки браузера
до него не доходит вовсе, поэтому выдать обращение за браузерное этот механизм
не может; от целевого сервиса скрыт лишь адрес клиента.

Смысл директив, следовательно, в сокрытии сведений **от промежуточных узлов и записей
на upstream**, а не от API. Оценивать их надо этой мерой.

### Адаптивная производительность

- **SMP workers** = количество vCPU (при > 1)
- **memory_pools_limit** = 50% предела памяти службы в бюджете узла
- **cache_mem** = 25% того же предела
- **read_timeout** — предел ПРОСТОЯ туннеля: соединение закрывается после часа без передачи данных, и таймер переармируется при каждой передаче — активный обмен не прерывается. Умолчание шаблона и значение образца совпадают: 1 час. Совпадение намеренно — развёртывание без переменной не должно давать более короткого предела, чем задумано

## Доказательство реализации

### Конструктивное

Шаблон генерирует полноценную конфигурацию Squid с условными блоками (Jinja2 `{% if %}`) для каждой feature. Механизм upstream-балансировки использует userhash для sticky sessions с автоматическим failover. Анонимизация заменяет заголовки, имитируя реальный браузер Chrome.

### Эмпирическое

- Валидация конфигурации при деплое: параметр `validate: 'squid -k parse -f %s'` в task
- Ручное тестирование: curl через прокси с/без аутентификации, к разрешённым/запрещённым доменам
- Рендер шаблона через Ansible: `tests/test_proxy_transit.py` в наборе `python3 -m unittest discover -s tests -p 'test_*.py'` (WSL, из `Servers/deploy`). Прогон 2026-11-06: запущено 115, упал 1, пропущено 20. Упавший тест к шаблону не относится: он выполняет `chown`, недоступный в WSL без root, и падает так же на чистом HEAD. Блок пулов покрывают 13 тестов рендера:
  - пул с единственным upstream и строки `cache_peer_access`;
  - пулы по умолчанию;
  - отказ пользователю вне пулов и место этого правила выше разрешающих;
  - пул без upstream и пул без пользователей;
  - отказ всем при отсутствии активных пулов;
  - отсутствие ACL пулов без аутентификации;
  - дробление длинного списка имён;
  - общий upstream двух пулов и объединённый ACL;
  - `nonhierarchical_direct off` в режиме запасного прямого пути;
  - остановка при упразднённом `squid_upstream_hosts` и при ошибке модели пулов.
- Нативная проверка на Squid 6.14: `python3 tests/check_proxy_pools_native.py` -- 965 запросов, 0 нарушений

### Негативное

- **Отказ upstream** -- connect-fail-limit=2 + dead_peer_timeout=15s обеспечивают быстрое обнаружение и переключение
- **Утечка IP** -- полное удаление proxy-заголовков (X-Forwarded-For, Via, X-Real-IP)
- **Анализ на участке до upstream** -- замена User-Agent и добавление полного набора браузерных заголовков
- **Пользователь вне пулов** -- явный 403 выше разрешающих правил, прямой выход не выполняется и при `allow_direct_fallback: true`
- **Пул без пользователей** -- ACL для него не выпускается, и `cache_peer_access` на него не ссылается. Иначе Squid не принял бы конфигурацию из-за ссылки на неопределённый ACL
- **Рендер без вычисленных пулов** -- останавливается ошибкой вместо молчаливой конфигурации «отказ всем»
- **Зависание AI API** -- предел простоя настраивается (умолчание 1 час). Обдумывание ответа простоем не является, пока сервис шлёт данные; предел закрывает соединение, по которому не передаётся ничего
