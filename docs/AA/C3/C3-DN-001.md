# C3-DN-001 — DNS Resolver (Unbound)

## Описание

Кеширующий DNS-резолвер (Unbound) развёртывается на каждой ноде инфраструктуры. Реализует каскадную архитектуру DNS-резолвинга: upstream-ноды резолвят через публичные DNS, access-ноды пересылают запросы на upstream unbound. Squid использует `dns_nameservers 127.0.0.1`.

### Каскадная архитектура

```
Публичные DNS (9.9.9.9, 8.8.8.8, 1.1.1.1)
          ↑
upstream: unbound (127.0.0.1:53 + ansible_host:53)
          ↑
access:   unbound (127.0.0.1:53) → forward → upstream unbound
          ↑
Squid:    dns_nameservers 127.0.0.1
```

### Ключевые решения

- **Access → upstream:** access-ноды НЕ резолвят через публичные DNS напрямую, а пересылают на upstream unbound. Это обеспечивает единую точку выхода в DNS и упрощает фильтрацию.
- **DNSSEC:** валидация включена по умолчанию (`auto-trust-anchor-file`).
- **systemd-resolved:** отключается автоматически при обнаружении (занимает порт 53).
- **Авторасчёт ресурсов:** потоки = CPU cores, кеш = RAM/32 (мин 16 MB).
- **Закрытый резолвер:** внешний слушатель upstream доступен только access-нодам — на сетевом уровне (firewall) и на прикладном (`access-control`). Открытый резолвер был бы и точкой утечки запросов инфраструктуры, и плечом отражённого трафика.

### Интерфейсы


**Спецификации контрактов:**

- [C3-DN-001-Config](../Interfaces/User/C3-DN-001-Config.md) — разрешение имён

| Интерфейс | Описание | Кто допущен |
|---|---|---|
| `127.0.0.1:53` | Локальный DNS для Squid и системы (все ноды) | только сама нода (`127.0.0.0/8 allow`) |
| `ansible_host:53` | Внешний DNS для access-нод (только upstream) | IP из `dns_allowed_clients` (группа `access_proxies` + `dns_extra_clients`) |

### Ограничение доступа: два уровня

| Уровень | Механизм | Реакция на чужой запрос |
|---|---|---|
| Сеть | UFW / nftables / iptables на upstream: 53/tcp и 53/udp только с IP из `dns_allowed_clients` ([C4-PB-001](../C4/C4-PB-001.md), [C4-TM-004](../C4/C4-TM-004.md)) | пакет отбрасывается (DROP), счётчик попыток растёт |
| Приложение | `access-control` в `unbound.conf`: `/32 allow` на клиента, `0.0.0.0/0 deny` ([C4-RL-004](../C4/C4-RL-004.md)) | запрос отбрасывается без ответа |

Оба уровня используют один и тот же список клиентов, вычисляемый в `playbook.yml`, — так правило не расходится между бэкендами firewall и конфигурацией unbound. Ограничение проверяется на самой ноде после развёртывания: задача читает действующие правила ядра, а не шаблон.

### Конфигурация

| Параметр | Значение | Описание |
|---|---|---|
| `dns_resolver_port` | 53 | Порт unbound |
| `dns_resolver_dnssec` | true | DNSSEC-валидация |
| `dns_resolver_min_ttl` | 300 | Минимальный TTL (5 мин) |
| `dns_resolver_max_ttl` | 86400 | Максимальный TTL (24 ч) |
| `dns_resolver_neg_ttl` | 60 | Negative TTL |
| `dns_resolver_prefetch` | true | Обновление популярных записей до истечения TTL |

## Два уровня кеширования имён

Резолвер узла — не единственное место, где оседают разрешённые имена. Собственный кеш
ведёт и Squid, обращаясь к резолверу лишь при промахе:

| Уровень | Положительный ответ | Отрицательный ответ | Чем задан |
|---|---|---|---|
| Squid | 6 часов | 30 секунд | Директивы конфигурации Squid |
| Резолвер узла | от 5 минут до 24 часов, в пределах срока от авторитетного сервера | 60 секунд | Переменные роли |

Сроки заданы порознь и между собой не согласованы. Практическое следствие: смена адреса
у домена может не замечаться **до шести часов**, даже если авторитетный сервер объявляет
короткий срок жизни записи, — верхний кеш держит прежний адрес и к резолверу
не обращается. Для служб, меняющих адреса при балансировке, это заметная величина.

Обратная сторона того же: перезапуск резолвера либо очистка его кеша не влияют
на обращения, которые Squid разрешит из собственного кеша.

Число сегментов кеша округляется вниз до ближайшей степени двойки: unbound принимает
здесь только её и при ином значении округлял бы сам, сообщая об этом в журнале
сообщением, неотличимым по виду от неисправности. Округление вниз, а не вверх:
сегментов больше числа потоков не нужно — они лишь дробят память.

## Критерии приёмки

| # | Критерий | Метрика / Способ проверки | Целевое значение |
|---|----------|---------------------------|------------------|
| 1 | Unbound запущен и слушает | `systemctl is-active unbound` | active |
| 2 | Squid использует локальный DNS | `grep dns_nameservers /etc/squid/squid.conf` | `127.0.0.1` |
| 3 | DNS-резолвинг работает | `dig @127.0.0.1 anthropic.com` | NOERROR |
| 4 | Access → upstream forwarding | `dig @127.0.0.1 anthropic.com` на access-ноде | Ответ от upstream unbound |
| 5 | DNSSEC валидация | `dig @127.0.0.1 dnssec-failed.org` | SERVFAIL (невалидный DNSSEC) |
| 6 | DNS upstream доступен access-ноде | `dig @<upstream> example.com` и `dig +tcp @<upstream> example.com` с access-ноды | NOERROR по обоим транспортам |
| 7 | DNS upstream закрыт для посторонних | те же запросы с хоста вне `dns_allowed_clients` | timeout по обоим транспортам (не REFUSED) |
| 8 | Список клиентов соответствует инвентори | `nft list set inet filter dns_clients` / `iptables -S SQUID-PROXY \| grep 53` / `ufw status` | ровно IP группы `access_proxies` |

### Аналитическое

**Выбор Unbound:** лёгкий, безопасный (DNSSEC из коробки), хорошо подходит для forwarding/caching. Альтернативы: BIND (избыточен для caching-only), dnsmasq (слабее DNSSEC).

**Каскадная архитектура:** access-ноды не выходят в публичный DNS напрямую — весь DNS-трафик проходит через upstream, что обеспечивает единую точку контроля и снижает DNS-утечки.

### Негативное

| Риск | Митигация |
|---|---|
| Upstream unbound недоступен | Unbound пытает все forwarders; при полном отказе upstream — Squid fallback на DNS timeout |
| DNS-спуфинг | DNSSEC-валидация включена по умолчанию |
| Порт 53 занят systemd-resolved | Автоматическое отключение stub listener в роли |
| Открытый резолвер (утечка запросов, отражённый трафик) | Firewall: 53/tcp+udp только с IP access-нод; `access-control … deny` в unbound; ограничение проверяется на ноде после развёртывания |
| Разрыв локального резолвинга запретом порта 53 | Loopback разрешён (`iif "lo"` / `-i lo -j RETURN`) выше запрещающих правил во всех бэкендах |
| Расхождение списка клиентов между бэкендами | Единый источник `dns_allowed_clients` в `playbook.yml` для firewall и unbound |
