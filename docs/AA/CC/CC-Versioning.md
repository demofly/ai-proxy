## Схемы версионирования

| Схема | Формат | Применение |
|---|---|---|
| **CalVer** | `YYYY-MM-DD` | Документация, архитектурные артефакты |
| **SemVer** | `MAJOR.MINOR.PATCH` | Внешние компоненты с собственным версионированием |
| **Git SHA** | 40-символьный хеш коммита | IaC-артефакты (Ansible playbook, templates, roles) |
| **OS Package** | Версия из пакетного менеджера | Компоненты, устанавливаемые через APT/репозиторий |

## Политика версионирования

### Документация

- Версия документации привязана к дате коммита в git (CalVer: `YYYY-MM-DD`).
- Каждое значимое изменение документации фиксируется в [CC-Changes.md](CC-Changes.md).
- Версионирование API: **N/A** — проект не предоставляет API; является инфраструктурным прокси-сервисом.

### IaC-артефакты (Ansible)

- Версия Ansible playbook, ролей и шаблонов определяется хешем коммита git (Git SHA).
- Семантическое версионирование не применяется: playbook не является библиотекой и не публикуется.
- Для отката к предыдущей версии используется `git checkout <SHA>`.

### Внешние компоненты

- **mtg (MTProxy):** версия задана номером в `mtproxy_version`. Установка — **версионированный каталог с переключением символьной ссылки**: бинарник кладётся в `/usr/local/lib/mtg/{версия}/mtg`, `/usr/local/bin/mtg` — ссылка на него, путь из `ExecStart` юнита не меняется. Смена номера ведёт к переустановке и перезапуску службы; прогон с прежним номером не делает ничего. Откат — возврат прежнего номера: каталог предыдущей версии остаётся на узле, повторная загрузка не нужна. Целостность архива проверяется при заданном `mtproxy_sha256` (пусто — проверка не выполняется).
- **OS-пакеты:** устанавливаются из официальных репозиториев. Режимом ведает флаг inventory `service_upgrades_enabled` (умолчание `true`): прогон доводит пакеты до последней доступной версии (`state: latest`) и остаётся идемпотентным — при неизменившемся репозитории повторный прогон ничего не делает. Значение `false` замораживает версии на установленных (`state: present`) и сводит только конфигурацию. Фиксация через APT pinning **не применяется**: она превратила бы отставание версий в невидимое, а не в решённое.

### Правила обновления

1. **Минорные обновления** OS-пакетов — допускаются без ADR, выполняются рядовым прогоном.
2. **Мажорные обновления** (смена major-версии компонента) — требуют ADR и тестирования на стенде.
3. **Обновление mtg** — требует проверки совместимости с текущими клиентами MTProxy: несовместимость обнаруживается уже после перезапуска, поэтому откат подготовлен заранее (см. схему с символьной ссылкой выше).
4. **Перезапуск как последствие.** Обновление пакета службы перезапускает её сценарием пакета — до и помимо Ansible. Задачи установки служб несут `throttle: 1`: узлы обновляются по одному, и пара access-нод под VIP (равно как и пара upstream-резолверов) не уходит в перезапуск разом.
5. **Владение разделяемыми службами узла.** `nginx` и `CrowdSec` на узле по одному экземпляру. На узле совместного размещения их версию двигает **только проект-владелец**; второй проект держит у себя `service_upgrades_enabled: false` либо не разворачивает соответствующую роль. Иначе два прогона будут двигать версию общей службы по очереди, каждый перезапуская её у соседа.
6. **Правила детектирования CrowdSec** обновляются независимо от флага, при каждом прогоне: отставшие правила не ловят текущие атаки, а служба при этом выглядит работающей.
7. **Обновления безопасности** выполняет `unattended-upgrades` (только источники обновлений безопасности, автоматическая перезагрузка запрещена): ждать очередного прогона Ansible ради закрытия уязвимости нельзя.
