# TD-Logs — Таксономия журналов

**Последняя правка AI:** 2026-08-29T06:55:30Z

## Описание

Перечень журналов, которые ведут узлы инфраструктуры: где они лежат, кто их пишет, кто читает и что с ними происходит дальше. Документ отвечает на два вопроса эксплуатации — куда смотреть при разборе происшествия и какие журналы содержат сведения, требующие защиты.

Событийная сторона (что именно попадает в журналы) описана в [TD-Events.md](TD-Events.md); сущность записей журнала доступа — [DE-LG-001](../DD/DE/DE-LG-001.md).

## Журналы служб

| Журнал | Расположение | Пишет | Уровни | Содержит сведения ограниченного доступа |
|---|---|---|---|---|
| Журнал обращений Squid | `/var/log/squid/access.log` | Squid, при каждом обращении | — (формат `squid`) | Да: адреса клиентов, имена пользователей, имена узлов назначения |
| Журнал работы Squid | `/var/log/squid/cache.log` | Squid | отладочный, информационный, предупреждения, ошибки | Нет |
| Журнал CrowdSec | `/var/log/crowdsec/crowdsec.log` | Агент обнаружения | информационный, предупреждения, ошибки | Частично: адреса нарушителей |
| Журнал применителя решений | Журнал systemd юнита `crowdsec-firewall-bouncer` | Применитель решений | информационный, ошибки | Частично: адреса нарушителей |
| Журнал резолвера | Журнал systemd юнита `unbound` | unbound | информационный, ошибки | Да: запрашиваемые имена, если поднят уровень подробности |
| Журнал nginx | `/var/log/nginx/error.log` | nginx | предупреждения, ошибки | Нет: маршрутизатор работает на уровне соединений и адресов не журналирует |
| Журнал MTProxy | Журнал systemd юнита `mtg` | mtg | информационный, ошибки | Частично: адреса подключающихся клиентов Telegram |
| Журнал Keepalived | Системный журнал (`syslog`) | Keepalived | информационный | Нет |
| Журнал проверки Squid | Системный журнал, метка `keepalived-chk` | Сценарий проверки | информационный | Нет |
| Системная аутентификация | `/var/log/auth.log`, журнал systemd юнита `ssh.service` | sshd, PAM | информационный, предупреждения | Да: адреса и имена, с которых входили на узел |

## Различие по уровням проксирования

| Журнал | Access-узел | Upstream-узел |
|---|---|---|
| Журнал обращений Squid | Ведётся при `enable_logging` | **Отключён**: `access_log none`, `cache_log /dev/null` |
| Журнал работы Squid | Ведётся | Отключён вместе с предыдущим |
| Прочие журналы служб | Ведутся | Ведутся |

Отключение журналирования на upstream — не оптимизация, а требование анонимности: узел вне РФ не должен хранить сведений о том, кто и куда обращался ([C2-NF-002](../C2/C2-NF-002.md), [ADR-000001](../ADR/ADR-000001.md)). Побочное следствие: обнаружение вторжений на upstream опирается только на системные журналы.

## Кто читает журналы

| Читатель | Что читает | Зачем |
|---|---|---|
| Агент CrowdSec | Журнал обращений Squid (только access), `auth.log`, журнал systemd `ssh.service` | Обнаружение подбора паролей, сканирования, эксплуатации уязвимостей |
| DevOps-инженер | Все перечисленные | Разбор происшествий, проверка состояния |
| Служба ИБ | Журнал обращений, журналы CrowdSec | Аудит обращений и реакции на угрозы |

Источник для агента обнаружения порождается **условно**: журнал обращений
попадает в его список источников только при `proxy_role: access` и `enable_logging: true`.
Отсюда следствие для эксплуатации: включение журналирования прогоном, из которого роль
обнаружения исключена, даёт журнал, который никто не читает — агент работает, журнал ведётся,
обнаружение по обращениям не действует, и внешних признаков у этого состояния нет
([C4-PB-001](../C4/C4-PB-001.md), выборочное развёртывание по тегам).

## Обращение с накоплением

Положение складывается из двух решений, принятых порознь:

| Средство | Состояние | Откуда известно |
|---|---|---|
| Встроенная ротация Squid | **Выключена намеренно**: `logfile_rotate 0` с пояснением «управляется системой» | Шаблон конфигурации |
| Системная ротация проекта | `/etc/logrotate.d/squid-aiproxy` | Период `squid_log_rotate_period`, глубина `squid_log_rotate_keep`, сжатие, усечение на месте |
| Системная ротация из поставки Squid | Неизвестно: пакет дистрибутива обычно приносит собственную настройку | Требует осмотра узла |

Отсюда практическое следствие: **утверждать, что журнал не ротируется, нельзя** — как
и обратное. Проект ротацией не занимается, встроенное средство выключено, а действует ли
настройка из поставки пакета, проверяется только на узле командой
`ls /etc/logrotate.d/squid`.

Если она отсутствует, журнал обращений растёт неограниченно, и на узле с длительной
работой это приведёт к исчерпанию места на разделе.
