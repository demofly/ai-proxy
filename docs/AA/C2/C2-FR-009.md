# C2-FR-009 — Пулы пользователей и upstream

## Описание

Пул связывает группы пользователей с набором upstream-узлов. Пользователь выходит в интернет только через upstream пулов своих групп. Access-узлы общие: все access применяют одни и те же пулы, переопределения на отдельный access нет.

### Формулировка (EARS)

1. **Повсеместное.** Access-прокси направляет запрос аутентифицированного пользователя только через upstream из объединения наборов всех пулов, с которыми связана хотя бы одна группа пользователя.
2. **Нежелательное поведение.** Если объединение наборов пулов пользователя пусто, access-прокси отклоняет его запрос с HTTP 403. Прямой выход с access-узла при этом не выполняется, даже при `allow_direct_fallback: true`.
3. **По событию.** При развёртывании с недопустимым описанием пулов развёртывание на access-узлах останавливается до первой задачи, меняющей узел, при любом наборе тегов. Недопустимое описание включает ссылку на неизвестную группу или неизвестный upstream, пользователя группы, отсутствующего в `passwd`, а также заданный прежний перечень `squid_upstream_hosts`.
4. **По состоянию.** Пока inventory не задаёт `proxy_pools`, действуют два пула по умолчанию: `default` и `reserve`.

### Модель

| Сущность | Атрибуты | Ограничения |
|---|---|---|
| Группа пользователей (`proxy_user_groups`) | имя группы, список имён пользователей | имя `^[A-Za-z0-9][A-Za-z0-9_.-]{0,63}$`, имя `all` зарезервировано. Имя пользователя `^[A-Za-z0-9][A-Za-z0-9._@+-]{0,127}$`, повторы в группе запрещены. Каждое имя обязано быть в `passwd` |
| Пул (`proxy_pools`, элемент списка) | `name`, `groups`, `upstreams` | ровно эти 3 ключа. `name` — `^[a-z][a-z0-9_-]{0,31}$`, уникально. `groups` — список групп либо особая группа `all` (все пользователи `passwd`). `upstreams` — список узлов группы inventory `upstreams` без повторов либо строка `all` (вся группа на момент развёртывания) |
| Набор upstream пользователя (выводимый) | объединение `upstreams` пулов пользователя | пустой набор даёт отказ 403 |

Пулы по умолчанию:

```yaml
# AI-GENERATED — NOT REVIEWED: SECTION START
proxy_user_groups: {}
proxy_pools:
  - {name: default, groups: [all], upstreams: all}  # все пользователи, все upstream
  - {name: reserve, groups: [], upstreams: []}      # пуст по пользователям и по upstream
# AI-GENERATED — NOT REVIEWED: SECTION END
```

### Предпроработка (§C2.4)

**Типовые атрибуты.** Опись: идентификатор, состав, ссылки на upstream, порядок, владелец, статус, срок действия, источник, ПДн. В область вошли идентификатор (`name`), состав (`groups`, списки пользователей) и ссылки на upstream. Порядок пулов на маршрутизацию не влияет: действует объединение. Владелец — оператор inventory, отдельного атрибута нет. Статус и срок действия не вводятся: пул действует, пока описан в inventory. Имена пользователей — идентификаторы, поэтому описание пулов хранится в частном `inventory.yml`, а не в репозитории.

**Типовые сценарии.** В область вошли:
- создание пула;
- перевод группы между пулами;
- пользователь в нескольких пулах (объединение);
- пользователь вне пулов (отказ 403);
- пул без upstream (отказ 403 его пользователям, если других пулов у них нет);
- пул с upstream без пользователей (upstream не объявляется);
- удаление upstream из inventory при ссылке на него в пуле (остановка развёртывания);
- опечатка в имени пользователя или группы (остановка развёртывания);
- миграция с `squid_upstream_hosts` (остановка с указанием переноса);
- добавление upstream в inventory (пул с `upstreams: all` получает его без правки).

Вне области — массовая загрузка, импорт и экспорт: описание правится в inventory. Конкурентная правка закрывается контролем версий оператора. Отмена изменения — повторным развёртыванием прежнего описания.

**Типовые жизненные циклы.** Описание пулов проходит состояния: «описано в inventory» → «проверено» (pre_tasks на access-узлах, сверка с `passwd`, при любом наборе тегов) → «отрендерено» в `squid.conf` (`squid -k parse`) → «применено» (reload Squid). Отказ на любом переходе оставляет действовать прежнюю конфигурацию access-узла.

## Критерии приёмки

| # | Критерий | Метрика / Способ проверки | Целевое значение |
|---|----------|---------------------------|------------------|
| 1 | Пользователь пула ходит только через upstream своего пула | нативная проверка: ≥20 запросов пользователя пула с одним upstream | 100 % ответов от upstream пула |
| 2 | Пользователь двух пулов получает объединение | нативная проверка: запросы пользователя групп двух пулов | ответы только от upstream этих пулов |
| 3 | Пользователь с пустым набором получает отказ | запрос пользователя вне пулов и пользователя пула без upstream | HTTP 403, обращения к upstream нет |
| 4 | Без учётных данных — прежний запрос аутентификации | запрос без `Proxy-Authorization` | HTTP 407 |
| 5 | Пулы по умолчанию сохраняют прежнее поведение | рендер без `proxy_pools`: все пользователи, все upstream | `cache_peer` на каждый upstream, отказа по пулу нет |
| 6 | Ошибка описания останавливает развёртывание до изменения служб | рендер с неизвестной группой, неизвестным upstream, повтором, отсутствующим в `passwd` пользователем, заданным `squid_upstream_hosts` | прогон завершается ошибкой, конфигурация не записана |
| 7 | Все access рендерят одинаковые пулы | рендер двух access из одного inventory | одинаковые блоки ACL и `cache_peer_access` |

## Доказательство реализации

### Конструктивное

- Фильтр `aiproxy_pools` ([filter_plugins/pools.py](../../../Servers/deploy/filter_plugins/pools.py)) проверяет описание и разрешает пулы до изменения служб.
- Шаблон [squid-access.conf.j2](../../../Servers/deploy/templates/squid-access.conf.j2) выпускает ACL `aiproxy_pool_<имя>` на каждый пул с пользователями и upstream. Для каждого upstream он выпускает `cache_peer_access`, а для пользователей с пустым набором — правило `http_access deny authenticated !aiproxy_routed all`.

### Аналитическое

Выбор модели и отклонённые альтернативы — [ADR-000010](../ADR/ADR-000010.md).

Критерий 7 держится устройством кода, а не тестом. Блок пулов шаблона [squid-access.conf.j2](../../../Servers/deploy/templates/squid-access.conf.j2) читает только `_squid_pools`, группу inventory `upstreams` и переменные upstream-узлов. `_squid_pools` вычисляется из `proxy_pools` и `proxy_user_groups`, а прежний перечень на узел `squid_upstream_hosts` останавливает развёртывание. Переменных, задаваемых на access-узел, блок не читает. Рендера двух access из одного inventory со сравнением блоков нет — см. «Верификация».
