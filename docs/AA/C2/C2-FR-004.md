# C2-FR-004 — Кеширование ответов

**Последняя правка AI:** 2026-08-29T06:22:39Z

## Ссылки

- Родительские требования C1: [C1-BC-001](../C1/C1-BC-001.md)
- Дочерние требования C3: [C3-SA-001](../C3/C3-SA-001.md)

## Описание

Система реализует дисковое кеширование ответов HTTP на уровне **access-прокси**.

**Граница применимости, определяющая ценность механизма.** Основной трафик проекта — туннели `CONNECT` к AI API, содержимое которых зашифровано сквозным TLS между клиентом и целевым сервисом ([DE-TR-001](../DD/DE/DE-TR-001.md)). Такой трафик кешированию не поддаётся в принципе, поэтому кеш работает лишь для обычных запросов HTTP, если они есть. Ожидать заметной доли попаданий в кеш на обращениях к AI API не следует — это не признак неисправности.

Назначение кеша при таком раскладе — снижение задержки повторных запросов и нагрузки на каналы к upstream. Кеширование включается условно и не применяется на upstream-уровне.

### Механизм кеширования

![Механизм кеширования Squid: оценка кешируемости, ufs, условное включение](diagrams/C2-FR-004-caching-flow.svg)

> Исходник: [diagrams/C2-FR-004-caching-flow.puml](diagrams/C2-FR-004-caching-flow.puml)

1. Access-прокси Squid получает ответ от upstream (или из кэша).
2. Squid оценивает кешируемость ответа по HTTP-заголовкам (Cache-Control, Expires, Last-Modified).
3. При положительной оценке ответ сохраняется в дисковом хранилище (ufs).
4. Последующие идентичные запросы обслуживаются из кэша без обращения к upstream.

### Конфигурация кэша

| Параметр | Значение | Описание |
|---|---|---|
| `cache_dir` | `ufs /var/spool/squid[/${process_number}] 100 16 256` | Тип ufs, 100 MB, 16 директорий L1, 256 L2; номер процесса в пути — при числе ядер больше одного |
| `maximum_object_size` | 50 MB | Максимальный размер кешируемого объекта |
| `enable_caching` | `true` (access) / `false` (upstream) | Условное включение |

### Условное включение

Кеширование включается переменной `enable_caching` (по умолчанию `true` на access-уровне). При `enable_caching: false` директива `cache_dir` исключается из конфигурации, добавляется `cache deny all`, и Squid работает в pass-through режиме.

**Правила свежести** заданы под характер ответов API. Порядок значим — применяется
первое совпавшее правило:

| Правило | Значение |
|---|---|
| Статика документации сервисов (`gif`, `png`, `jpe?g`, `ico`, `svg`, `css`, `js`, `woff2?`) | 1440 мин / 20 % / 10080 мин |
| Всё прочее (`.`) | 0 / 0 % / 0 — ответ не считается свежим ни секунды без явных заголовков |
| Порядок применения | Первое совпавшее правило; шаблон статики стоит выше |

Второе правило — существо меры: решение о повторном использовании ответа API принимает
целевой сервис своими заголовками, а не прокси своими умолчаниями. Умолчания Squid
рассчитаны на статику и дали бы обратное. Защищённые обращения не кешируются вовсе,
поэтому правила касаются только незащищённых.

### Дисковый кеш и многопроцессный режим

Две настройки заданы порознь и разумны каждая сама по себе, а вместе дают неучтённое
ограничение:

| Настройка | Условие | Значение |
|---|---|---|
| Многопроцессный режим | Ядер больше одного | Рабочих процессов по числу ядер |
| Дисковый кеш | Кеширование включено | Один каталог хранилища `ufs` |

Хранилище `ufs` не рассчитано на совместный доступ нескольких процессов, поэтому путь
каталога **разводится по номеру процесса**: при числе ядер больше одного шаблон выпускает
`cache_dir ufs /var/spool/squid/${process_number} ...`, и каждый рабочий процесс получает
собственное хранилище. Подстановку номера выполняет сам Squid. Инициализация структуры
(`squid -z`) создаёт каталоги под все процессы; признаком выполненной работы служит
каталог первого из них.

Проверено на стенде (узел с двумя ядрами, кеширование включено): созданы каталоги `1`
и `2`, каждый процесс сканирует свой (`Done scanning /var/spool/squid/1 dir`), жалоб
на совместный доступ в журнале нет, служба работает.

## Критерии приёмки

| # | Критерий | Метрика / Способ проверки | Целевое значение |
|---|----------|---------------------------|------------------|
| 1 | Директория кэша создаётся при развёртывании | ls -la /var/spool/squid | Директория существует с корректными правами |
| 2 | Размер кэша соответствует конфигурации | grep cache_dir /etc/squid/squid.conf | `ufs /var/spool/squid 100 16 256`, при нескольких ядрах — с `/${process_number}` в пути |
| 3 | Повторный запрос обслуживается из кэша | Два идентичных **обычных запроса HTTP** (не CONNECT); проверка TCP_HIT в access.log | TCP_HIT для второго запроса |
| 4 | Кеширование отключено на upstream | grep cache_dir на upstream-ноде | Строка отсутствует |

## Доказательство реализации

### Конструктивное

Реализовано в `Servers/deploy/templates/squid-access.conf.j2`:
- Условный блок `{% if enable_caching %}` включает `cache_dir ufs` с фиксированным размером 100 MB.
- При `enable_caching: false` — `cache deny all`.
- Инициализация кэша: `squid -z` выполняется Ansible-задачей при первом развёртывании.

### Аналитическое

**Выбор ufs:** стандартный тип хранилища Squid, использующий синхронный I/O. При текущих объёмах кэша (100 MB) переход на `aufs` (асинхронный) или `rock` (SSD-оптимизированный) не оправдан.

**Фиксированный размер:** 100 MB — достаточен для кеширования статических ресурсов AI-сервисов (JS, CSS, шрифты). Основной трафик — CONNECT-туннели (HTTPS), которые не кешируются.

### Негативное

| Риск | Митигация |
|---|---|
| Кеш выдаёт устаревшие ответы | Правила свежести заданы под характер ответов API: без явных заголовков ответ не считается свежим ни секунды, и решение о повторном использовании принимает целевой сервис, а не прокси своими умолчаниями. Статика документации сервисов кешируется отдельным правилом |
| Переполнение диска | Размер кэша ограничен формулой; Squid автоматически вытесняет старые объекты (LRU) |
| Кеширование чувствительных данных | CONNECT-туннели (HTTPS) не кешируются Squid; кешируются только HTTP-ответы |
